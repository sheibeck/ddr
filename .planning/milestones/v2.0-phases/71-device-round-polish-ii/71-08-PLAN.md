<objective>
Let the player read their status effects during a fight (POLISH-11, D-16). The plan folds in the source todo `.planning/todos/pending/2026-09-21-status-chit-tap-in-combat-shows-nothing-rail-hidden-in-comba.md`, and the SUMMARY must name it. Moving that todo to `.planning/todos/done/` is the orchestrator's job after merge (D-13). This plan does not move it.

Purpose: the user reported that "when I'm in combat and I tap on a status chit the rail does not show up, so I have no way to see my status effect descriptions in combat." The cause is that renderRail hides the rail whenever `S.combat` is set, so the chip's rail card has nowhere to show. 71-04 built one combat-legal card, the long-press foe card: it shows over the combat screen at z 8 and is lifted above the actions (71-05 re-pointed the lift to the what-happened strip). D-16 reuses that path:
- a hero chit tap in combat raises a combat-legal condition card with the same description it shows out of combat;
- foe condition descriptions are read from the long-press details card, one line per effect;
- every other card stays hidden in combat.

Output:
- the pure rail.js card kind and predicate;
- foe condition descriptions in foeConditions.js and the details card;
- the shell wiring (the chip guard, the combat routing, and renderRail generalised from foe-only to the combat card kinds);
- the tests;
- the section M rows.

71-04 is merged by the time this runs. Read `.planning/phases/71-device-round-polish-ii/71-04-SUMMARY.md` for the real names before editing. This plan is written against 71-04-PLAN.md's card API and commit a712583: `foeCardUp`, `window.__mzFoeInspect`, `window.mzInspectFoe`, `#mw-rail[data-over="combat"]`, `--mw-rail-lift`, foeDetails.js `effectsLine` and `FOE_DETAILS_COPY.noEffects`. Where the merged names differ, follow the merged code and record the mapping in the SUMMARY. Read 71-05-SUMMARY.md for the lift (it reads #cb-summary's top first) and 71-07-SUMMARY.md for the tapGuards / `__mzTapArmed` seam.

Planner rulings (record in the SUMMARY):
- **R-28: the condition card.**
  - rail.js gains `COMBAT_CARD_KINDS = ["foe", "cond"]` and `isCombatCard(card)`. The combat-legal rules 71-04 wrote for the foe card now apply to any combat card: shown over the combat screen, lifted, shown at once (never typed), held until dismissed while the combat screen is up, and given the normal hold once it is gone.
  - Only the foe card is re-derived live, because a condition description is static text.
  - A "cond" card is pushed only while the combat screen is up. Out of combat the chip keeps today's exact `window.mzRailLine?.(label.toUpperCase(), explainText, "info", 8400, "·")` call, so its typed card and hold are unchanged.
- **R-29: reading a chit never skips (D-16 asks the planner to choose).**
  - The chit strip `#mm-conditions` sits outside `#enc-panel`, so beatHurryTap never sees it. Reading a status is an inspection, like 71-04's long press (R-17). The card rises at once and the round keeps playing.
  - To make that possible, the chip no longer uses guardTap's `encArmed()` (false for a whole beat, and re-armed at every beat line's render). It uses its own `condArmed()`: the same 250 ms Phase 32 window, measured from the chip-set change that paintConditions already detects.
  - The new `guardInfoTap(btn, fn, armed)` registers that predicate in 71-07's `tapGuards`, so a chit tap mid-round clicks (it acts).
  - It stamps no `aria-disabled` marker. The arm sweep never covered `#mm-conditions`, so guardTap's marker made TalkBack announce every chip as disabled for good; this closes that as part of the same surface.
  - The `function guardTap(btn, fn)` head and every decision button stay as they are.
- **R-30: foe chips.**
  - A foe's chips are text inside its card's tag line (`chipsFor` maps them to text) with no listener of their own, so a tap on a chip is a tap on the card and aims at that foe, as today. Nothing here adds a chip listener, and a tap never raises a card.
  - A foe condition's description is read from the long-press card: each current effect gets its own line, `<chip text> — <desc>`, in table order. The desc comes from the one 71-03 table.
- **R-31: "the combat screen is up".** `combatScreenUp()` is `!!(S && (S.combat || window.__mzBeat?.active?.()))`. The last round's playback runs after the engine has already cleared `S.combat`, but the combat screen is still showing. This predicate keeps a card raised then over the combat screen, instead of at z 4 under the overlay. It drives the chip's routing and renderRail's data-over/lift and hold decisions. The `hidden` predicate only swaps foe-only for combat cards.
- **R-32: which descriptions are the hero chips'.** The vocabulary is every `key: "…"` literal in engine/derived.js `conditionsOf`, plus every content/activations.js `ACTIVATION_OF` kind with `effect > 0` (fly shows as flight; kinds with `effect: 0`, such as half, stone and knit, never make a live chip). Copy is added only where the test finds a key falling back to `CONDITION_EXPLAIN.default`, in the house voice. When a new key also has no CONDITION_COPY label, add the label, because it is the card's title. Record every row added.
