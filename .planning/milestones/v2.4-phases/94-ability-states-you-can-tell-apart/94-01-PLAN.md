ASTATE-04's engine half: one pure, derived function that says which of the four states an ability is in, how many rounds are left and why it cannot be used, for any sheet (hero or Joiner), plus its twin for the Bard's Sing. useAbility and sing() are refactored onto them so the label the view will show (plans 94-03/94-04) and the refusal a tap produces can never disagree. Implements these CONTEXT decisions (94-CONTEXT.md):
- "Engine contract": a pure derived `abilityState(state, sheet, key)` in `engine/abilities.js` returning `{ state: "ready" | "recharging" | "unavailable" | "spent", roundsLeft, reason }`, built from the existing `isReady`, `abilityRoundsLeft`, `abilityShortfall` (what `abilityUnavailableReason` reads) and `abilityTargetShortfall` checks; `useAbility`'s refusals use the same function; no rng draw; nothing serialized (no `*Comparable()` change); parity fixtures must not move.

- "Surfaces": the Bard's Sing row is in scope, so Sing gets `singState(state)` (Sing is not in ABILITY_BY_ID; RESEARCH Pattern 3).
- ROADMAP criterion 4: "a tap always agrees with the label". RESEARCH Finding F4: Last Stand's hp gate is a real rung (the menu never showed it); it is in abilityState.

Claude's discretion used:
- Rung order is the ladder's own, notFought FIRST (RESEARCH's rung table, order 0). The research prototype checked ownership before pending; that would disagree with useAbility (refuseIfPending fires first even for a key the hero does not own), so this plan puts the pending rung first.
- No class check inside abilityState (hero tests build sparse sheets with no `cls`); the off-class filter stays pickMemberAbility's (RESEARCH Pattern 4).
- `heroOut` (the hero-cannot-act menu) is ignored: that shape replaces the whole menu and engine.js converts any action to loseTurn, so it never shows ability rows (CONTEXT Claude's Discretion; RESEARCH "Hero cannot act").
