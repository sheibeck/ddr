<objective>
Close the combat gear hole in the engine (GRULE-01). While a fight is up, the engine refuses every gear change a player can reach, with one `gearRefused { reason: "combat" }` event and the line "Not the moment to change outfits." Then prove that the lock moves no parity fixture.

Purpose: the user's Pixel 7 report ("I didn't think we should allow changing equipped gear during combat"). Phase 63 greys the sheet's EQUIP/SWAP/UNEQUIP rows on this engine reason, and it can read the new `gearLockReason(state)` predicate to do it.

Implements CONTEXT "Combat gear lock (GRULE-01)":
- Lock window: `state.combat` set, `combat.pending` included.
- Gated verbs: `equipItem` (the targeted jewelry/cloak swap included) and `unequipSlot`. `wearItem` stays an ungated primitive.
- One new event, `gearRefused`, with zero rng draws and the state untouched.
- USE, potions, scrolls, the Shield and Drop stay live.

**Planner ruling (derived from CONTEXT's own test clause, not a new product decision).** CONTEXT asks for a test proving "no dispatchable action changes c.weapon/c.armor/c.worn while state.combat is set", and it states that `wearItem`'s callers never run mid-fight. At the engine level that premise is false in two cases:
- A multi-foe fight parks a kill's drop in `state.pendingLoot` while `state.combat` is still set (`engine/combat.js#killFoe` → `offerLoot`), so `takeLoot { equip: true }` or an auto-wearing `takeLoot`/`takeAllLoot` could change gear mid-fight.
- A `pendingFind` can linger into a fight (`move()` does not block on it), so `takeFind` could too.

The shell never shows the loot or find card while `S.combat` is set, and the bot resolves combat first, so a player cannot reach either path. To make the premise an engine fact, this plan also gates `takeFind`, `takeLoot` and `takeAllLoot` behind the same combat gate, with their own verb on the same event. `wearItem` itself stays ungated, exactly as locked. Nothing changes for players or for the bot.

Output: the combat gate plus `gearLockReason` in `engine/items.js`, narration rows in both tables, a new unit suite, a zero-move measurement recorded in FIXTURE-INVENTORY.md with a standing guard, and a docs note.
</objective>
