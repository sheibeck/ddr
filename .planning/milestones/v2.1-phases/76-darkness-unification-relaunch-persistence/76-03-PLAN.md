## Flagged assumptions (surfaced, not silently decided)

- **pendingJoiner keeps the absent-key shape.** `newRun` never writes a `pendingJoiner` key (only meetJoiner and resolveJoiner do), so the loaders emit it only when the save carries the key: a valid offer or null. Adding it to newRun instead would touch the three local parity comparables for no gain.
- **Validation depth (Claude's discretion per CONTEXT).** Deep enough that the next fight or store action cannot throw on a structurally broken value: src/browser/engineAdapter.js#dispatch's catch replaces the WHOLE run with a fresh one on a throw, so a shallow check would turn a bad stored fight into a lost character. Shallow enough to carry every genuine field wholesale.
- **A fight and a store both valid:** the store is dropped (the engine never opens a store mid-fight).
- **A dropped party member invalidates a stored fight with allies**, because the allies' `partyIdx` would point at the wrong sheet.
- **Canon referral:** untrusted save JSON and prototype pollution are canon security concerns, covered by validateSave's existing fail-closed contract and /gsd-secure-phase; not minted here.
