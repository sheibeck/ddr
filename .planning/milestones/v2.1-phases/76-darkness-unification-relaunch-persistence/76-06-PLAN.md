<objective>
Make Map the Floor last only until the hero moves. This comes from the user's 2026-09-26 ruling, recorded in 76-CONTEXT.md under "User rulings after planning": "revealing the dungeon spell should last only until you move. Then you lose focus and map stops being revealed. it's pretty powerful to be able to map your way around and move." No existing v2.1 requirement covers it, so `requirements` is empty and the orchestrator adds a REQUIREMENTS entry. The todo is `.planning/todos/pending/2026-09-26-map-the-floor-lasts-only-until-you-move.md`.

After a cast, the hero studies the whole floor while standing still. The first step onto another square breaks the focus: the floor re-fogs through the existing Phase 40 sweep, and every cell the hero actually walked or saw stays seen. Only movement ends it. Recasting refreshes it, a relaunch keeps it, and a scroll of Map the Floor follows the same rule.

Purpose: the spell becomes a snapshot you study, not a map you navigate by. The spell text, the chip, the Gear row and the Oracle and rail lines all say so in voice.

Output: a one-square window on the existing squares timer, a countdown-free chip, a tolerant load clamp, rewritten copy, a new pin file, the traced and declared bot-pin moves, and the Plan 06 subsection in FIXTURE-INVENTORY.md.
</objective>

## Flagged assumptions (surfaced, not silently decided)

- **The seam is the existing squares timer (the todo's own suggestion).** Map the Floor gets `squares: 1`, so the Phase 40 path (tickSquares -> the `spell:reveal` effect-to-null transition -> refogSpellSeen -> revealFaded) fires on the first step. There is no new flag and no new expiry code. tickSquares has exactly one call site in engine/ (movement.js#move, reached by the `move` and `useTool` actions), so "only movement ends it" holds by construction, and a Task 1 test pins that single call site.
- **A teleport is not a step.** teleport() never ticks the window (the Phase 40 pin stays). Every in-game teleport (a teleporter tile, or a dot's Teleport or Insanity roll) runs from a step's feature dispatch, after that step has already ended the window. The one way a window can survive a teleport is a cast made during a fight that interrupted a step onto a teleporter, because RULES-12's pending tile resolves after the fight. There the hero is flung, not stepping, and their first real step ends it. If the user wants a teleport to break focus too, that is one line in teleport().
- **A refused step is not a step.** A wall bump, a one-way refusal and a hazard-choice card (the climb/ladder decision) all leave the hero where they stood, so the window stays. A crossing that lands on the far side, including a failed climb that survives, is a step.
- **Stepping onto the stairs ends the window first.** revealFaded fires before the descent (move ticks before feature dispatch). The new floor starts fogged as always.
- **Old saves: a clamp, not a ceremony.** `clampRevealWindow` loads a live record with more than one square left as left 1, with no event and no narration. Without it, an old mid-window save would keep its old 40-square window: a second rule in all but name, with a chip already claiming "until you move". If the user prefers a pure tolerant load, the helper can be deleted.
- **Relaunch, checked against 76-03.** The `spell:reveal` record is squares-cadence. Today's clearStaleTimers removes only rounds records. 76-03 changes it to keep rounds records when a fight survives, and squares records survive in every branch. clearStaleSpellSeen keeps the flags while the record is live (phase effect, left above 0), and left 1 is live. 76-03's resumed fight therefore brings back a window cast on the fight's square, and 76-04's generic resume walk already compares `c.timers` and the floor on every sampled state. The clamp never changes a state the new engine produces, so 76-04's resume-determinism proof is unaffected.
- **The chip has no countdown.** conditionsOf's reveal chip becomes `{ key: "reveal", polarity: "good" }`. The shell gains a generic fixed-detail slot on a CONDITION_COPY row, and only reveal uses it.
- **The floorMapped event drops `squares`.** There is nothing left to count, and no narration reads it. The bot's `observe` reads only the event type.
- **The bot keeps its policy (no tools/lib/tuning-bot.mjs edit).** A Magic User still casts Map the Floor once per floor when its charges are plentiful. The bot's exit search already knows where the stairs are (an omniscience it has always had), so a human's main gain from the snapshot is already priced into the bot. Under the old rule, the whole-floor map left the bot with no unseen tile, so it random-walked for up to 40 squares after each cast. Now it resumes normal exploration after one step. Runs that cast will move, and each move is traced and declared. The balance effect is measured in Phase 79.1.
- **No balance readouts** (user ruling 2026-09-26). Deterministic tests and the state pins cover the rule.
