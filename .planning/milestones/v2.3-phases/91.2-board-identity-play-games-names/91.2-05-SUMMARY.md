# Phase 91.2 Plan 05: Identity v2, the verified-name writer, a handle-free boardSync and the shared rig Summary

The rolled-handle identity is replaced by a Play Games board session: the client signs in through the PlayIdentity seam, links the 2.2.0 anonymous account (or adopts its runs), claims the verified name from the boardName function before anything posts, follows renames and account switches, and `boardWrites.submitRun` posts under that name. The handle, the re-roll and the rewrite path are gone from the identity, boardWrites and boardSync. Nothing was deployed and no live call was made.

## What the identity does now

- **Record** `ddr.identity.v2`: `{ v: 2, uid, refreshToken, idToken, expiresAtMs, linked, playerId, name, overridden, adoptFrom }`. `sanitizeIdentity` is tolerant (an invalid uid clears tokens, linked, playerId, name and overridden; names go through `sanitizeBoardName`). A v1 record is migrated on first load: uid and tokens kept, handle dropped, v1 key removed; a v1 record with no uid (just a handle) is simply removed.
- **boardSession({ interactive })** returns `{ ok: true, uid, idToken, name }` or `{ ok: false, reason }` with reason in `off | offline | server | refused | unavailable | signin`. Compete-gated always, single-flight (an interactive request queued behind a failed quiet one still gets its prompt). Compete OFF, a missing seam, an unconfigured playConfig (empty webClientId) and an unconfigured Firebase config answer with zero calls; a signed-out player answers `signin` with no network call. PlayIdentity reasons map config/unavailable to unavailable, denied to signin, error to server; Identity Toolkit OPERATION_NOT_ALLOWED to unavailable, a network failure to offline, 429/5xx and other 4xx to server.
- **Link / adopt (BOARD-32).** Covered on the rig: uid kept (the claim stamps the seeded @handle runs), a link that returns a new uid (G3 fallback), and a player already linked elsewhere (second sign-in without idToken, adopt, anonymous account deleted). An interrupted adopt keeps `adoptFrom` and finishes next session.
- **Claim (D-06).** A session is complete only after a claim returned a name. The `needsCode` retry, the single `auth` refresh-and-retry and the NOT_LINKED / ADOPT_REFUSED handling are pinned by tests.
- **Rename (G2).** A changed Play Games name re-signs-in and re-claims; with `refreshProviderName: false` the client unlinks (`accounts:update` deleteProvider) and relinks once; a failed relink returns the held name and is not repeated in the launch; admin-overridden names are never chased.
- **Account switch.** The stored session is dropped locally (never adopting the other player's runs) and the new player gets their own uid and name; switching back returns to the first player's uid and name.
- **Bug reports.** `getToken({ explicit: true })` with Compete OFF signs up anonymously and never calls Play Games (tested).
- **No token in any result or log:** the module has no console calls (source check) and failure results are tested for token substrings.

## boardWrites / boardSync

- `submitRun` builds with `session.name` and passes a session failure's reason through unchanged (`WRITE_REASONS` gains `signin`). After the GET-settled check shows a genuine refusal it calls `refreshName()` once and, when the name moved, retries once (a second refusal is returned, no loop).
- `eraseMyRuns` is unchanged in shape; `identity.deleteAccount()` now releases the name first. `boardSync.erase()` re-seeds nothing.
- `RETIRED_KEYS` is exactly `["ddr.pgsqueue.v1", "ddr.handleRewrite.v1"]`; each literal appears once in boardSync.js.
