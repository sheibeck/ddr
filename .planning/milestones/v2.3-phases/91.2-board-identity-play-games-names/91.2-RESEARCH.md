# Phase 91.2: Board Identity: Play Games Names Replace Rolled Handles - Research

**Researched:** 2026-09-30
**Domain:** Play Games Services v2 sign-in in a Capacitor 8 Android shell; Firebase Auth (Identity Toolkit) federated sign-in and account linking over plain REST; Firestore security rules as the only server; a scheduled trusted job on the Spark plan; Play Data safety and privacy wording
**Confidence:** MEDIUM overall. The building blocks are verified. Four behaviours can only be proven on the device and the live project (listed under "Spike gates").

## Summary

The phase can be built without the Firebase SDK and without leaving the Spark plan, but not in the naive way. The naive way is to put the Play Games name in the ID token and check `request.auth.token.name` in the rules. **That check is not a verification:** `name` is the account's top-level `displayName`, and any signed-in user can rewrite it with their own ID token through `accounts:update` [VERIFIED: docs.cloud.google.com identity-platform accounts.update, "Requests from administrators and end users are supported"]. The only Play Games fact a client cannot forge is the **linked identity**: once Firebase has exchanged a real server auth code, the ID token carries `firebase.identities["playgames.google.com"]`. The rules can check that key (so a 2.2.0 anonymous token is refused), but they cannot learn the name from it.

**Primary recommendation:**

1. **Sign in.** A small in-repo Java Capacitor plugin (`PlayIdentity`) wraps Play Games Services v2 (`play-services-games-v2` 22.1.0). It exposes `status`, interactive `signIn` and `serverAuthCode`. The shell sends the code to `accounts:signInWithIdp` over REST with `postBody=code=…&providerId=playgames.google.com`. When a 2.2.0 anonymous identity exists, the same call carries that `idToken`, which **links** the account: the uid is kept, so every 2.2.0 run stays owned by the same uid.
2. **Rules.** A run create needs `'playgames.google.com' in request.auth.token.firebase.identities`, and its `handle` must equal the name in a new admin-only `names/{uid}` document (or `''` while that document does not exist yet). No client may update a run. Owner delete stays.
3. **The trusted name writer.** A scheduled GitHub Action runs every ~15 minutes, in the same style as the existing bug-report Action (zero dependencies, a service-account key in a repo secret). It reads each linked account's Play Games display name from Identity Toolkit (`projects/{p}/accounts:batchGet` → `providerUserInfo`, which Google fills from the IdP, not the client). It writes `names/{uid}`, stamps that name onto every run of the uid (2.2.0 `@handle` runs included), and fills the `''` placeholders.
4. **Rollout.** The Phase 87 transition rules file is extended so it accepts either the 2.2.0 shape or the new Play Games shape for the device-test window. The final rules, which refuse 2.2.0, go live when 2.3 reaches testers. That is already `docs/RELEASING.md` "Release 2.3.0" step 3.

The one real cost of staying on Spark is **latency**: a brand-new player's name, or a changed name, reaches the board on the next Action run (about 15 minutes, up to ~30 with GitHub cron jitter). The Blaze-plan alternative, a callable Cloud Function, removes the lag but needs a billing account. **Open decision D1.**

**Plugin surface (all four methods resolve and never reject into the UI):**
- `init()`: `PlayGamesSdk.initialize(activity.getApplication())`, idempotent. Called only while Compete is ON.
- `status()`: `GamesSignInClient.isAuthenticated()`; if true, `PlayersClient.getCurrentPlayer()` → `{ signedIn, playerId, displayName }`.
- `signIn()`: the interactive `GamesSignInClient.signIn()`, used only from a player-tapped SIGN IN row.
- `serverAuthCode({ serverClientId })`: `GamesSignInClient.requestServerSideAccess(serverClientId, /*forceRefreshToken*/ false)` → `{ authCode }`. It uses the no-scopes overload, so no consent screen appears. The consent screen shows only when EMAIL, PROFILE or OPEN_ID is requested [CITED: developer.android.com/games/pgs/android/server-access]. **Never request PROFILE or EMAIL**: those scopes return the Google account's real name and email.

**Facts:**
- PGS v2 sign-in is **automatic and silent**: "When the game launches, the Play Games Services v2 SDK automatically and silently authenticates the platform" [CITED: developer.android.com/games/pgs/android/migrate-to-v2]. On failure, PGS retries by itself. A manual button is optional; `signIn()` is the manual path. There is **no sign-out** in v2 [CITED: same page]. A first-ever user may see a profile-creation sheet [CITED: developer.android.com/games/pgs/android/android-signin; `SUPPRESS_GAME_PROFILE_CREATION` meta-data exists, and we should not set it].
- Google's documentation recommends `PlayGamesSdk.initialize` in `Application.onCreate` [CITED: android-signin]. **Lazy initialisation from a plugin method is [ASSUMED] to work.** Prove it in the spike. If it does not, initialise in the plugin's `load()` gated by a native-readable flag.
- Manifest: `<meta-data android:name="com.google.android.gms.games.APP_ID" android:value="@string/game_services_project_id"/>` [CITED: android-signin]. Values: `517177834262` if the old configuration is reused (G4), otherwise the new configuration's id.
- Google says: "Don't store the player ID from the Android SDK on your backend … untrusted devices can tamper" [CITED: android-signin]. This is the documented reason to verify server-side (Q2).
- **Is the gamer name unique?** Yes: "Customize your profile with a unique gamer name and avatar" [CITED: support.google.com/googleplay/answer/2954594]. **Can it change?** Yes, any time (play.google.com/games/profile or Play Store settings) [CITED: same]. Supervised (child) accounts get auto-generated names only [CITED: same]. Private profiles still expose "profile image, gamertag" [CITED: support.google.com/googleplay/answer/16562063]. Gamer names appear to be a single word without spaces [ASSUMED].
- **Player IDs** are per PGS project ("a different Player ID for each game … consistent for a given game across devices") [CITED: developer.android.com/games/pgs/next-gen-player-ids]. A NEW PGS configuration (G4 path B) gives every player a new id. That is harmless, because nothing stored today uses PGS ids.

## Q2. Server verification without the Firebase SDK

**Recommendation: `accounts:signInWithIdp` over REST with the Play Games provider enabled.** Confidence: MEDIUM. The REST `postBody` form for Play Games is undocumented but confirmed live to route to the provider (see "Evidence").

```
POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithIdp?key=<FIREBASE_CONFIG.apiKey>
{ "requestUri": "http://localhost",
  "postBody": "code=<serverAuthCode>&providerId=playgames.google.com",
  "returnSecureToken": true,
  "returnIdpCredential": true,
  "idToken": "<anonymous idToken>"   // present only to LINK (Q4)
}
→ 200 { localId, idToken, refreshToken, expiresIn, federatedId, providerId, displayName, photoUrl, isNewUser, ... }
```

- The field meanings come from the Identity Platform reference: `idToken` means "the user's account at the IdP will be linked to the account represented by this ID token"; `returnIdpCredential` makes `FEDERATED_USER_ID_ALREADY_LINKED` come back as a readable `errorMessage` [CITED: docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/signInWithIdp]. The `code=…&providerId=playgames.google.com` form is community-reported [CITED: groups.google.com/g/firebase-talk/c/3_hhLejFncw, June 2023, LOW] and confirmed by the live probe to reach the provider [VERIFIED].
- After sign-in, the existing `securetoken` refresh flow (`firebaseAuth.js#doRefresh`) keeps working unchanged. A new server auth code is needed only to sign in or link again. An auth code is single-use and short-lived [ASSUMED, the OAuth norm], so the exchange must be single-flight and run immediately after the code is obtained.
- **Configuration needed:**
  1. PGS configuration in Play Console, with an **Android** credential (the Play App Signing key's SHA-1, plus the debug keystore SHA-1 for the debug APK) and a **Game server** credential (an OAuth client of type **Web application**) [CITED: developer.android.com/games/pgs/android/server-access; firebase.google.com/docs/auth/android/play-games].
  2. Enable the Firebase Play Games provider with that web client's **ID and secret**. Claude can do this with the admin API: `POST https://identitytoolkit.googleapis.com/v2/projects/delve-die-repeat-6ba5f/defaultSupportedIdpConfigs?idpId=playgames.google.com` body `{ "enabled": true, "clientId": "…", "clientSecret": "…" }`, with a gcloud token and `x-goog-user-project`. This is the same technique 83-08 used for Anonymous; the user supplies the secret.
  3. The web client ID (public) ships in the app as `serverClientId`, in e.g. `src/browser/firebaseConfig.js` or `content/`.
  4. The OAuth consent screen (Branding plus Audience = External, **In production**) in the cloud project that owns the credentials. GAMES_LITE is non-sensitive, so no verification is needed [ASSUMED].
  5. The existing API key already allows Identity Toolkit and Token Service (83-08), and `signInWithIdp` is Identity Toolkit, so no key change is needed.
  6. Setting the SHA-1 in Firebase project settings is only for Firebase SDK apps; the REST flow does not need it [ASSUMED].
- **Spark:** Firebase Authentication providers, Play Games included, work on Spark. **Cloud Functions do not**: "Cloud Functions is only available on the Blaze plan" [CITED: firebase.google.com/docs/projects/billing/firebase-pricing-plans]. Enabling a supported IdP does not need an Identity Platform upgrade (Anonymous was enabled the same way) [VERIFIED: project config shows the legacy `signIn` block].
- **What the ID token carries** [CITED: firebase.google.com/docs/rules/rules-and-auth]: `sub` = uid; `firebase.identities` = a map from provider to an id array (so `firebase.identities["playgames.google.com"][0]` = the Play Games player id [ASSUMED for this provider; the pattern is documented for google.com]); `firebase.sign_in_provider`; `name` = "The user's display name, if set". **`name` is client-writable** (`accounts:update` accepts `displayName` from the end user [VERIFIED: accounts.update docs]), so the rules must never trust it. `firebase.identities` is written only by Google on a successful IdP exchange, so it is trustworthy. The user can remove it themselves (`accounts:update deleteProvider`), which only locks them out of posting.

## Q3. Binding the displayed name to the identity

**Recommendation: an admin-only `names/{uid}` authority, maintained by a scheduled GitHub Action, plus rules that bind every run's `handle` to it.** Confidence: MEDIUM (it depends on G1 and G2).

| Option | Verdict |
|---|---|
| `request.auth.token.name` | **Rejected.** It can be forged with one `accounts:update` call |
| **A. Scheduled GitHub Action (Spark)** | **Recommended**, unless the user accepts Blaze. It reuses the existing pattern (`.github/workflows/bug-reports.yml`: Node 22, zero deps, a service-account JWT in a repo secret). Latency is about 15 to 30 min for a new or renamed name |
| B. Cloud Function (Blaze), e.g. a callable `claimName` (verifies the ID token with the Admin SDK, reads the user's Play Games `providerData` or calls the Games API, writes `names/{uid}` and stamps runs) | Instant, but needs Blaze (a billing account), a `functions/` codebase, Cloud Build and Artifact Registry. Also the fallback if G1 fails |
| C. Client-supplied name bound only to a verified player id | Fails "verified, not trusted from the client". Any modified client could post someone else's name under its own id |
| D. Google Apps Script web app as a free relay | Works in principle (`accounts:lookup` with the user's token, then a Firestore write as the owner), but it adds a new ops surface, quotas and CORS quirks. Not recommended |

**Rules (final, `firebase/firestore.rules`):**

```
function hasPlayGames() {
  return request.auth != null
    && 'identities' in request.auth.token.firebase
    && 'playgames.google.com' in request.auth.token.firebase.identities;
}
function namePath(uid) { return /databases/$(database)/documents/names/$(uid); }
function verifiedName(uid) { return exists(namePath(uid)) ? get(namePath(uid)).data.name : ''; }

match /runs/{runId} {
  allow get: if true;
  allow list: if request.query.limit == null || request.query.limit <= 50;
  allow create: if hasPlayGames()
    && request.resource.data.uid == request.auth.uid
    && runId == request.auth.uid + '_' + request.resource.data.hash
    && isValidBoardRun(request.resource.data)          // handle: string, size 0..64 (no @-regex)
    && request.resource.data.handle == verifiedName(request.auth.uid)
    && !exists(/databases/$(database)/documents/banned/$(request.auth.uid));
  allow update: if false;                               // no client rename: RE-ROLL and rewriteHandle are gone
  allow delete: if request.auth != null && resource.data.uid == request.auth.uid;  // ERASE, any account (2.2.0 included)
}
match /names/{uid} {
  allow get: if true;                                   // the client reads its own verified name before posting
  allow list, create, update, delete: if false;         // the Action / boards-admin only (IAM bypass)
}
```

- `in` on a map tests keys [CITED: firebase.google.com/docs/reference/rules/rules.Map]. Guard `'identities' in …firebase` so an anonymous token cannot hit a missing-key error [ASSUMED defensive].
- The field keeps the name **`handle`**, because shipped 2.2.0 clients decode `doc.handle` for the headline (`v2.2.0:src/browser/boardClient.js#decodeRunDocument` is tolerant). Keeping it means 2.2.0 players who browse the board after the cutover see the real Play Games names, not blank rows.
- The **Action** (`tools/board-names/sync-names.mjs` + `.github/workflows/board-names.yml`) does the following:
  1. Signs in with a service-account JWT (scopes: datastore + identitytoolkit). The service account needs `roles/datastore.user` + `roles/firebaseauth.viewer` (`firebaseauth.users.get` is required by `accounts:batchGet`) [CITED: docs.cloud.google.com identity-platform projects.accounts/batchGet; role name ASSUMED].
  2. Pages `GET /v1/projects/delve-die-repeat-6ba5f/accounts:batchGet?maxResults=1000` and keeps users with a `providerUserInfo` entry whose `providerId == "playgames.google.com"`. **Process only users whose `lastLoginAt` is newer than a `meta/nameSync` checkpoint.** Otherwise every run re-reads every `names/*` doc, and at about 1,000 players × 96 runs a day that exceeds the Spark 50k reads/day.
  3. For each changed name: writes `names/{uid} {name, updatedAt}` (unless a moderation `override` is set), then rewrites `handle` on every `runs` doc of that uid whose handle differs. This covers the 2.2.0 `@handle` runs of linked players and the `''` placeholders.
  4. Deletes `names/{uid}` when the auth user no longer exists (after ERASE MY RUNS deleted the account).
  5. Flags names that hit `content/safety-wordlist.js` (Q9).
- **Name source:** `providerUserInfo[].displayName` is written by Google from the IdP, and end users cannot edit it through `accounts:update`, which changes only the top-level `displayName` [ASSUMED; the spike checks with a tampering attempt].

## Q4. Migrating 2.2.0 players

**Recommendation: link first, then merge by re-posting on collision.** Confidence: MEDIUM (G3).

1. On the first successful PGS sign-in with Compete ON, if `ddr.identity.v1` holds an anonymous `uid` + `refreshToken`: refresh it to a live `idToken`, get a server auth code, and call `signInWithIdp` **with `idToken`**. On success the uid is unchanged, the account stops being anonymous, and every 2.2.0 run, `reportLimits/{uid}` and bug-report history stay attached. The Action later renames all of that uid's runs to the Play Games name. **No client-side rewrite is needed**, so the whole `rewriteHandle` / `HANDLE_REWRITE_KEY` path is deleted (BOARD-32).
2. **`FEDERATED_USER_ID_ALREADY_LINKED`** means this Play Games player is already linked to uid C (a second device, or a reinstall that already linked). The code is spent, so get a **fresh** code and call `signInWithIdp` without `idToken`, which yields uid C. While still holding anonymous uid A's tokens, **merge**:
   - read A's runs (public list, `uid == A`, pages of 50);
   - re-create each under C (`C_{hash}`, `deepKey` recomputed with the new formula, the original `version` and `when` kept, `handle = verifiedName(C)`);
   - delete A's runs with A's token (owner delete), then `accounts:delete` A.
   Re-creating is idempotent through the doc id. This path also covers a reinstall that has local runs.
3. A player who never updates keeps uid A with `@handle` runs. See open decision D4 for what the board does with them after the cutover.
4. Storage: `ddr.identity.v1` → **v2** `{v:2, uid, refreshToken, idToken, expiresAtMs, pgs: {playerId, linked:true} | null}`. The loader tolerantly keeps the v1 uid and tokens (they are needed to link) and drops `handle`. Save the Play Games player id from the sign-in response, or decode the ID-token payload, so the shell can detect a **Play Games account switch** on the device (the `status().playerId` differs from the stored one) and sign in again.

## Q5. Name changes

A rename happens in Google's UI, and Firebase learns about it only at a later IdP exchange. The plan:

1. At each Compete-ON boot (and on resume, throttled), compare `status().displayName` (local, for display only) with `names/{uid}.name` (a public GET).
2. On mismatch, get a fresh code and call `signInWithIdp` again, which re-signs in the same uid. G2 checks that this refreshes `providerUserInfo.displayName`. If it does not, **unlink and relink** (`accounts:update {idToken, deleteProvider:["playgames.google.com"]}`, then `signInWithIdp` with `idToken`).
3. The next Action run rewrites `names/{uid}` and every one of the uid's runs.

The player's own rows show the local name at once. Everyone else sees it after the Action runs. Uniqueness holds at every instant for the current names, because each Play Games player links to exactly one uid (a federated id is unique per project). A former name can be taken by someone else later, and the board always shows current names.

## Q6. Refusing 2.2.0 clients

- **What 2.2.0 sends** (tag `v2.2.0`): an **anonymous** token (`firebase.identities` has no `playgames.google.com`), `handle` matching the `@(…)(…)` regex, the OLD `deepKey`, and owner handle-only updates on re-roll.
- **Final rules (release cutover):** `hasPlayGames()` alone refuses every 2.2.0 create. The removed update path refuses 2.2.0 re-roll rewrites. The old `deepKey` is refused too. Owner **delete stays**, so a 2.2.0 player can still ERASE MY RUNS (the privacy deletion route), and bug reports stay anonymous and unchanged.
- **How 2.2.0 behaves when refused** [VERIFIED: `git show v2.2.0:src/browser/runQueue.js` / `boardWrites.js`]:
  1. A 403 is classified "ambiguous" → one public GET of `runs/{uid_hash}` → 404 → `refused`.
  2. The queue **drops** the entry and settles its hash (it never retries), logs a `console.warn` line, and shows no card.
  3. The death screen's "You placed X" line never appears. The account block still says ON THE BOARD, and local YOUR DEAD keeps the run.
  4. A pending re-roll rewrite is retried on every flush and refused each time (harmless, one query and one commit attempt per flush).
  Refusal is silent and non-destructive locally.
- **Transition window** (the precedent is `firebase/firestore.transition.rules`, Phase 87 BOARD-28; still undeployed, `docs/LEADERBOARDS.md` §14):
  - Extend that one file into `create = newShape || legacyShape`:
    - `newShape` = the final create above;
    - `legacyShape` = `!hasPlayGames()` + the 2.2.0 `isValidBoardRun` (the handle regex, and `deepKey` old or new).
  - `update` stays allowed only for `!hasPlayGames()` accounts with the regex handle (2.2.0 re-roll).
  - Deploy it just in time before the milestone-end debug APK with Compete ON (a 2.3 build cannot post under today's live rules, because its doc has no `@handle` and it may send `''`).
  - The final rules then follow at "Release 2.3.0" step 3, which already states "From this moment a 2.2.0 client's run is refused".
  - Rewrite `test/unit/firestore-transition-rules.test.js` to prove final ⊂ transition and that the legacy branch cannot be used by a Play Games-linked token.
  - Note: BOARD-28's "submissions from shipped 2.2.0 clients still rank correctly" now holds only during the transition window. The orchestrator should reconcile the requirement wording.
- **Recovering runs dropped in the window** (open decision D5): runs a 2.2.0 client posted between the final-rules deploy and its update were dropped server-side but kept locally, with their hashes in `ddr.runQueue.v1.settled`, which lists **only** Compete-ON runs. The 2.3 client can re-enqueue, once, the local-history runs whose hash is in that settled ledger. Runs already on the board answer "exists" (idempotent, same uid after linking); dropped ones are created. This respects the "Compete-OFF runs are never uploaded" ruling, because the ledger contains only runs that were enqueued with Compete ON.

### Anti-patterns to avoid
- **Trusting `request.auth.token.name`,** or any client-sent name. It can be forged through `accounts:update`.
- **Requesting PROFILE or EMAIL scopes** in `requestServerSideAccess`. They expose the real name and email.
- **Initialising the PGS SDK at launch with Compete OFF.** It repeats the 67-01 D-02 compromise.
- **Keeping a client rename path "for migration".** The Action stamps names; the client never updates runs.
- **Storing the Play Games player id on public docs.** It adds a public User ID for no gain.

## Common Pitfalls

1. **The `retire-sweep` test forbids `play[ _-]?games`, `pgs`, `gms\.games`, `games-ids`, `game_services_project_id`** in shipped code (`test/unit/retire-sweep.test.js:39-53`). Rework it to forbid only the retired leaderboard artefacts (`scoreTag`, `LEADERBOARD_IDS`, `globalBoards`, `boardScores`, `createSubmissionQueue`, `modbender`/`idleflowgames` unless D2 picks them). `store-listing.test.js:76` and `compliance-docs.test.js:93` pin the retirement too.
2. **An unpublished PGS configuration** means only testers can sign in. Publish it before the release reaches anyone else.
3. **Wrong SHA-1.** A Play-installed build needs the **Play App Signing** key's SHA-1, not the upload key's. The debug APK needs the debug keystore SHA-1. A mismatch makes sign-in fail silently (old runbook §3).
4. **The auth code is single-use.** Make the exchange single-flight. A retry after `FEDERATED_USER_ID_ALREADY_LINKED` needs a fresh code.
5. **Spark read quota in the Action.** Only process users whose `lastLoginAt` passed the checkpoint, and do not list `names/*` every run.
6. **`firebase.identities` missing on some tokens.** Guard with `'identities' in request.auth.token.firebase`.
7. **Name-change race.** `names/{uid}` changes between the client's GET and its create → 403 → the new client re-reads the name and retries once (do not let the queue drop it as "refused").
8. **A Play Games account switch on the device.** Compare the stored player id with `status().playerId`, and sign in again on mismatch (a different uid).
9. **The `@handle`-specific code:** `handleInitials` splitting against `content/handles.js`, the `isValidHandle` gates in `account.js`, `accountChip.js`, `runDoc.js` and `fakeBoardServer.js`, and `handlePatternSource` in the rules tests. Replace them with a verified-name validator. Keep the regex only in the transition branch until the cutover deletes it with `legacyDeepKeyOf`.
10. **GitHub disables scheduled workflows** in a public repo after 60 days with no activity (the `bug-reports.yml` header). Nothing is lost; names just stall.
