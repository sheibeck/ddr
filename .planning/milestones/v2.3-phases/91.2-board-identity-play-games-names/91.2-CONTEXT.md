## Phase Boundary

Friends recognize each other on the board: every player is named by their Google Play Games name, which is unique and verified by the server, not a rolled @handle that can repeat. Compete needs Play Games sign-in; nobody re-rolls a name; a player's 2.2.0 runs move under their Play Games name once they sign in on the update; a shipped 2.2.0 client is refused once the final rules are live; the store listing, Data safety form text and privacy policy say what the board shows.

Requirements: BOARD-31, BOARD-32, BOARD-33.

Scope: the app shell (`src/browser/`, `mazeworld.html`), the Android shell (`android/`), the Firebase rules and a new Cloud Function (`firebase/`, `functions/`), dev tools (`tools/`), docs, the store listing and the darktier-studio privacy pages. **Never** `engine/`, and never `content/races.js` / `content/classes.js` (Phase 91 is editing them in a worktree at the same time). The rules engine is untouched; there are no parity fixtures.

**Runs beside Phase 91.** Only plan 91.2-08 edits `mazeworld.html` (Phase 91 edits it too: expect a merge there). Every 91.2 plan leaves the test suite green at its own boundary, so a Phase 91 phase-close suite run never lands in a 91.2 red window.

<decisions>
## Implementation Decisions

### Locked by the user (91.2-DECISIONS-EARLY.md; not re-asked)
- **D-10 Identity:** the board names every player by their Google Play Games name ("Everyone needs a play games handle already"). No rolled handle, no fallback handle.
- **D-11 No re-roll:** RE-ROLL HANDLE and the handle rewrite path are gone ("Let's not let handle rerolls be thing").
- **D-12 Sign-in required:** Compete requires Play Games sign-in.
- **D-01 Name source = Cloud Function on Blaze:** a Firebase Cloud Function writes the trusted `names/{uid}` record the moment a player signs in (instant), not the scheduled GitHub Action. The project moves to Blaze (the user attaches billing in the console); Claude deploys the function on the user's go, just in time with the release, like the rules. Keep usage inside the free tier; set a budget alert.
- **D-02 Sign-in plugin:** a small in-repo Java Capacitor plugin `PlayIdentity` (init, status, signIn, serverAuthCode) on `play-services-games-v2`; the SDK starts only when Compete is ON. Not the community plugin.
- **D-03 Compete ON but not signed in:** runs are held in the queue and a SIGN IN row shows in the ☰ account block (and the title sheet); they post once signed in.
- **D-04 2.2.0 runs whose owner never updates:** stay on the board under their @handle; renamed if the owner ever updates and signs in.
- **D-05 Runs 2.2.0 dropped during the refusal window:** the updated client re-posts Compete-ON runs from its local settled-hash ledger that never reached the board.
- **D-06 First run waits for the name:** a new player's first run posts once their name exists; it is held in the queue until then.
- **D-07 Data safety, declared honestly:** the Play Games SDK's app diagnostics, plus Personal info → Name (the gamer name is shown publicly); User IDs reworded.
- **D-08 Name filter:** a gamer name containing a word on our safety list shows as a neutral placeholder on the board; the admin script can hide a run too.
- **D-09 Play Games configuration:** reuse the existing configuration (cloud project `delve-die-repeat`, 517177834262; the user deleted and changed nothing). Spike gate G4 proves it works with the Firebase project; fallback a new configuration linked to Firebase.
- **D-13 Refuse 2.2.0:** shipped 2.2.0 clients' runs are refused once the final rules are live; a transition rules file covers the device-test window. Built this milestone, before the release.
- **D-14 Live changes are user-gated and just in time:** Blaze, the provider enable, the function deploy and every rules deploy run only on the user's go, with the release build or before the milestone-end Compete-ON device test, whichever comes first (memory: backend deploys just in time; check shipped 2.2.0 / vc12 compatibility first).

### Claude's Discretion (decided here, recorded for the executors)
- **Zero-dependency function.** `functions/board-names/` is plain Node 22 ESM with no npm dependencies, deployed as a 2nd-gen Cloud Function (`boardName`, region `us-central1`) with `gcloud functions deploy` through `tools/board-names/deploy.mjs`. It verifies the caller by calling Identity Toolkit `accounts:lookup` with the caller's own ID token (Google validates the token server-side and returns the Google-written `providerUserInfo`), and writes Firestore over REST with the runtime service account's metadata-server token. Reasons: the project's zero-dependency tool pattern (bug-reports Action, `file-issues.mjs`, Phase 83's plain REST), no package-legitimacy surface, unit-testable with injected fetch. Fallback if the zero-dependency deploy is refused: add `@google-cloud/functions-framework` (Google's own package) as the one pinned dependency, after a package-legitimacy check.
- **The rules trust anchor is the `names/{uid}` document,** not an ID-token claim. Only the function (or the admin tool) writes it, and the function writes it only after Google confirms a `playgames.google.com` provider on the caller's account. A create needs that document and `handle == names/{uid}.name`. This removes the unproven token-claim assumption (A3) from the rules and lets the live smoke probe stay automatable (the admin seeds a probe name).
- **`names` and `nameOverrides` are closed to clients entirely** (read and write); the function returns the name to the client, which caches it.
- **Server-side adopt.** When linking the 2.2.0 anonymous uid fails with `FEDERATED_USER_ID_ALREADY_LINKED`, or the link returns a different uid, the client signs in as the linked uid and the function moves the anonymous uid's runs onto it (the caller proves ownership of the anonymous uid with its own ID token; only an account with no providers can be adopted). The client then deletes the anonymous account.
- **G1/A4 fallback built in:** the function has a `NAME_SOURCE` switch (`provider`, default; `games`). With `games` it answers `NEEDS_GAMES_CODE`, the client sends a fresh server auth code, and the function exchanges it with the web client secret, calls the Games API `players/me`, and requires the player id to equal the linked provider's `rawId`. Switching is a redeploy with one env var; no client update.
- **G2 fallback built in:** a rename (the local Play Games name differs from the claimed name) re-signs-in and re-claims; if the claimed name is still the old one, the client unlinks and relinks the provider once per launch.
- **G4 fallback cheap:** the APP_ID lives only in `android/app/src/main/res/values/games-ids.xml` and `PLAY_GAMES_CONFIG.appId`, the web client ID only in `PLAY_GAMES_CONFIG.webClientId` (both in `src/browser/firebaseConfig.js`); a test keeps the two APP_ID copies equal.
- **A6 fallback documented:** the plugin initializes lazily from its first method call; the plugin header names the switch (initialize in `load()` when the stored settings say Compete is ON) if lazy init fails on the device.
- **Identity storage:** `ddr.identity.v2`; a v1 record is migrated (uid and tokens kept so the link can happen, the handle dropped) and the v1 key removed. `ddr.handleRewrite.v1` joins `RETIRED_KEYS`.
- **Welcome card for everyone on 2.3:** a new setting `nameWelcomed` replaces `boardWelcomed`, so every player (2.2 players included) sees once that their Play Games name is now public on the board.
- **Held-runs notice:** one rail card per launch, at most, when Compete is ON and the player is not signed in (it is a decision prompt: sign in from the menu).
- **Masking (D-08):** `src/browser/nameFilter.js` flags a name when any token (split on non-letters, camelCase and letter-digit boundaries) equals a safety-list term, or the letters-only form contains a safety-list term of four or more letters that no allowlisted word explains. Flagged names render the `LEADERBOARD_COPY` placeholder and a neutral avatar. Tests never inline a banned word (they pick terms from the list at runtime).
- **Board avatars:** one generic initials rule for Play Games names and legacy @handles (`nameInitials` in `leaderboardView.js`); `content/handles.js` and `src/browser/handles.js` are deleted once nothing imports them.
- **Moderation tooling:** `boards-admin` gains `names [--flagged]`, `name-override <uid> <text>` and `name-clear <uid>`; hiding a run is the existing `delete-run` (documented as the hide route).
- **Function sizing:** `--max-instances=3`, 256 MiB, 60 s timeout; it writes only when the name changed; stamping and adopt page their runs.
- **Spike harness:** `src/browser/pgsProbe.js` behind a button in the hidden dev row (long-press the version label); non-invasive (it deletes only accounts it created); the report goes to an on-screen block and `console.info` (logcat), never a token.

<interfaces>
## Contracts every plan builds against

### `boardName` Cloud Function (HTTP, plan 91.2-02; emulated by the fake in 91.2-03)
- URL: `BOARD_NAME_FN.url` = `https://us-central1-delve-die-repeat-6ba5f.cloudfunctions.net/boardName` (`src/browser/firebaseConfig.js`).
- `OPTIONS` → 204 with CORS headers (`Access-Control-Allow-Origin: *`, `Access-Control-Allow-Headers: Authorization, Content-Type`, `Access-Control-Allow-Methods: POST, OPTIONS`, `Access-Control-Max-Age: 3600`). Every response carries the allow-origin header. Any other non-POST method → 405.
- `POST`, `Authorization: Bearer <Firebase ID token>`, JSON body:
  - `{ "op": "claim" }`, optionally with `"adoptIdToken": "<anonymous ID token>"` and/or `"gamesAuthCode": "<fresh server auth code>"`;
  - `{ "op": "release" }`.
- Claim 200: `{ "ok": true, "name": string, "overridden": boolean, "stamped": int, "adopted": int }`. Release 200: `{ "ok": true, "released": true }`.
- Errors `{ "ok": false, "error": CODE }`: 400 `BAD_REQUEST`; 401 `UNAUTHENTICATED` (missing, invalid or expired token); 403 `NOT_LINKED` (no `playgames.google.com` provider); 403 `ADOPT_REFUSED`; 409 `NEEDS_GAMES_CODE`; 403 `GAMES_MISMATCH`; 422 `NO_NAME`; 502 `UPSTREAM`; 500 `INTERNAL`.
- Firestore: `names/{uid}` = `{ name: string (1..64), updatedAt: timestamp }`; `nameOverrides/{uid}` = `{ name: string, at: timestamp }` (admin only). `BOARD_NAME_MAX_CHARS = 64`.
- Name sanitizing: NFC, drop control and format characters, collapse whitespace runs to one space, trim, cut to 64 UTF-16 units without splitting a surrogate pair; empty → `NO_NAME`.

### `PlayIdentity` (native plugin + JS seam, plan 91.2-01)
- JS: `createPlayIdentity({ loadPlugin })` and `createFakePlayIdentity({ signedIn, playerId, displayName, interactive })`; methods `init()`, `status()`, `signIn()`, `serverAuthCode({ serverClientId })`, all resolving (never rejecting): `{ ok, signedIn, playerId, displayName }` or `{ ok: true, authCode }` / `{ ok: false, reason }`.
- Fake server auth code: `fake:<encodeURIComponent(playerId)>:<encodeURIComponent(displayName)>:<n>` (n increments, so every code is single-use and distinct).

### Identity v2 (`src/browser/firebaseAuth.js#createIdentity`, plan 91.2-05)
`{ snapshot, getToken, forceRefresh, boardSession, signIn, refreshName, deleteAccount, drop }`; `boardSession()` → `{ ok: true, uid, idToken, name }` or `{ ok: false, reason }` with reason in `off | unavailable | signin | offline | server | refused`.
