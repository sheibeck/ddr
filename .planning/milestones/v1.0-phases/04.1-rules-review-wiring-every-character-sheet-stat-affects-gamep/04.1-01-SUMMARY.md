# Phase 04.1 Plan 01: Terminology Rename (skill points → experience points, Win Potential/wp → Hit Points/hp) Summary

Renamed every player-facing "skill point(s)" string to "experience point(s)"/"XP", and every player-facing "Win Potential"/"wp" string to "Hit Points"/"hp", across the live `mazeworld.html` app, the flavor/epitaph content tables, the engine's event narration, the character-sheet view model, and — the highest-risk site — the two engine-generated store-row label strings in `engine/economy.js`'s `openStore`. This closes a live split-brain bug: the HUD already said "HP" while the HERO character sheet said "Win Potential" for the same stat; the two screens now agree everywhere.

## What Was Built

**TERM-01 (skill points → experience points/XP):**
- `mazeworld.html`: the HERO sheet's `<dt>Skill points</dt>` label, the "notes" reference bullet, the embedded `EPITAPHS`/`SUB_NOTE` duplicate tables, the `killFoe`/`tableFour`/`parley` narration lines, and the HUD footer (renamed to the tight "XP" abbreviation, not the full phrase).
- `content/flavor.js` (`SUB_NOTE.Barbarian`, `SUB_NOTE.Apprentice`) and `content/epitaphs.js` (three `{sp}` epitaph templates — the `{sp}` token itself untouched, only the surrounding words changed).
- `src/browser/eventNarration.js`'s `spGained` builder (the pluralized "experience point(s)" noun) and `foeKilled`'s trailing unit (`sp.` → `XP.`, a consistency fix beyond the plan's literal wording — see Deviations).
- `src/browser/viewModels.js`'s `stats` array: the sheet-row `label` changed from `"SKILL POINTS"` to `"EXPERIENCE"` (the `key: "skillPoints"` internal identifier is untouched, per the plan's TEXT-ONLY constraint).

**TERM-02 (Win Potential/wp → Hit Points/hp):**
- `mazeworld.html`: the HERO sheet label (closing the HUD/sheet split), all inline race/class blurb duplicates, every skill/item/spell/bestiary `txt:`/`note:` description containing the "wp" unit, every `evt()`/`say()` combat-log line, the runtime-set upkeep/armor-kit-row text, and two dual-purpose data+lookup-key sites rewritten as atomic blocks so the display string and the code that matches it never drift apart:
  - Table Four's `ENCOUNTER_TABLES` row (`"+10 WP"`, `"+25 SP"`, …) and its `apply` object keys in `tableFour()` — renamed together to `"+10 HP"`/`"+25 XP"`/etc.
  - The `FAERIE` gift table's `"+d20 Base WP"`/`"-d10 Base WP"` strings and the two `gift === "..."` comparisons in `meetFaerie()` — renamed together to `"...Base HP"`.
- `content/flavor.js` (`RACE_NOTE.Elven/Troll`, `CLASS_NOTE.Fighter/Thief/Magic User`, and `SUB_NOTE.Knight` — the last one missed by 04.1-RESEARCH.md's occurrence count, found and fixed here) and `content/epitaphs.js` (two `wp`-unit epitaph templates in the `starve`/`poison` causes, also missed by the research audit).
- `src/browser/eventNarration.js`: all ~26 narration lines ending in the "wp" unit (`struck`, `struckByFoe`, `healed`, `rested`, `wentHungry`, `foodFound`, `potionDrunk`, `backfireSelfDamage`, `regenerated`, `acidTick`, `earthquakeSelfDamage`, `insaneStruckAlly`, `trapSprung`, `faerieBoon`/`faerieBane`, `afflictionCaught`, `deathCast`, `spellHit`, `allyStruck`, `foeFled`-adjacent `warlockBoost`, `summonBackfired`, `fellClimbing`, `fellInGorge`, `afflictionTick`, `leveled`'s `+N wp)` suffix, `cooked`).
- `src/browser/viewModels.js`: the `UPKEEP` stat's `"wp/day"` value → `"hp/day"` (the internal `winPotential` object/key is unchanged — it is never rendered directly, only `c.wp`/`c.maxWP` values feed it).
- `engine/economy.js`'s `openStore`: the food stock label template (`` `${f.n} (+${f.wp} hp)` ``) and the armor sub-label template (`` `AR ${a.ar}, ${a.wp} hp` ``) — the two RESEARCH-flagged "engine-generated, embedded in serialized state" risk sites. The underlying data fields (`f.wp`, `a.wp`, the `wp:` params object) are unchanged.

**Test/fixture updates (required by the plan's must_haves):**
- `test/unit/characterSheetViewModel.test.js`: added an assertion that the sp row's `label` is `"EXPERIENCE"` (not `"SKILL POINTS"`), changed the upkeep assertion's expected unit to `hp/day`, and renamed two test titles for accuracy.
- `test/unit/economy.test.js`: added two new tests (there were previously no assertions on the store label's exact text at all) proving the food stock label matches `/\(\+\d+ hp\)/` and never contains a bare `wp` unit, and the armor sub-label matches `/AR \d+, \d+ hp/` similarly.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1/2 — missed occurrences] Three sites the plan's file list / RESEARCH.md occurrence counts didn't catch**
- **Found during:** Task 2, while sweeping `content/epitaphs.js`, `content/flavor.js`, and `mazeworld.html` for every remaining `wp` unit occurrence.
- **Issue:** `content/epitaphs.js`'s `starve` and `poison` epitaph causes ("Cost of living: 4 wp a day...", "Died on an instalment plan, two wp per square.") and `content/flavor.js`'s `SUB_NOTE.Knight` blurb ("Nothing under 5 wp will come near you...") still said "wp"; RESEARCH.md's occurrence table only counted `RACE_NOTE`/`CLASS_NOTE`/`SUB_NOTE.Barbarian`/`SUB_NOTE.Apprentice` for flavor.js and didn't mention epitaphs.js's bare "wp" mentions at all. A fourth site, `mazeworld.html`'s `drinkPotion()` function (`say(\`Potion: +${amt} wp</span>...\`)`), used a different template shape than the `potionDrunk`-adjacent call site the audit had flagged, so my first bulk-rename pass missed it and a subsequent grep caught it.
- **Fix:** Renamed all four to "hp", identically to every other site.
- **Files modified:** `content/epitaphs.js`, `content/flavor.js`, `mazeworld.html`.
- **Verification:** Full-file `\bwp\b` grep re-run after the fix confirmed zero remaining display-text occurrences.

**2. [Rule 3 — blocking test, unanticipated by the plan] Parity suite byte-compares the engine's store label against the FROZEN prototype**
- **Found during:** the plan's own Task 2 verify block (`npm test`), which surfaced 2 failures (`test/parity/economy-parity.test.js` and `test/parity/full-suite.test.js`) not mentioned anywhere in the plan.
- **Issue:** `test/parity/harness/comparables.js`'s `stripStoreClosures` includes the store-row label string `n` (and `sub`) in its byte-for-byte prototype-vs-engine comparison. `test/parity/prototype-master.js.txt` is explicitly marked "FROZEN GOLDEN MASTER — DO NOT EDIT" and still emits the pre-rename "(+12 wp)"/"AR 3, 12 wp" text (it is a byte-verbatim snapshot of the ORIGINAL prototype, frozen specifically so later plans can't drift the parity reference). Renaming only the live engine's label (as TERM-02 requires) therefore created a permanent, unfixable-at-the-source textual divergence the parity harness would fail on forever.
- **Fix:** Added a `normalizeHpUnit()` helper to `test/parity/harness/comparables.js` that replaces `\bwp\b` → `hp` on both sides' store label/sub-label text immediately before comparison, documented with the exact rationale (this is the one permanent, deliberate, cosmetic divergence this rename creates; the frozen file cannot be touched). Every other field in the comparison (cost, sold, item identity, ordering) remains strictly compared — this does not weaken the parity check for anything except the one known, intentional wording difference.
- **Files modified:** `test/parity/harness/comparables.js` (NOT in the plan's `files_modified` list — added because it was the only way to satisfy both "rename the engine-generated label" and "npm test stays green" without touching the frozen golden master).
- **Verification:** `npm test` — both previously-failing tests pass; full suite 507/507.

### No architectural changes
Nothing here required a `checkpoint:decision` — every fix above was either a straightforward missed-text bug (Rule 1/2) or a minimal, well-scoped, documented test-harness normalization for a divergence this plan's own rename deliberately created (Rule 3). No state field, event-type identifier, or save shape was touched; `c.sp`, `c.wp`, `c.maxWP`, and every event type (`spGained`, `healed`, `struck`, `foeKilled`, …) are byte-for-byte unchanged.
