# Phase 04.1 Plan 04: Intelligence Gets a Mechanical Read (RULE-01) Summary

**Added an exported `intelBonus(c)` helper in `engine/derived.js` that raises `openChest`'s lock-roll success threshold for both the tiered-skill and bare-d20 paths, mirrored on the character sheet, with a test proving higher Intelligence opens a borderline lock that lower Intelligence does not.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-09T16:48:21Z
- **Tasks:** 1 (Task 1: Add intelBonus helper and apply it to the openChest lock roll)
- **Files modified:** 4

## Accomplishments

- `intelBonus(c)` — a pure, capped INT-scaled bonus exported from `engine/derived.js` (0 below intel 15, +1 at 15–19, +2 capped at intel 20, the max chargen roll)
- `openChest` (`engine/encounters.js`) now applies `intelBonus(c)` to the lock-roll `need` in BOTH the tiered Locks/lockpick path and the bare-d20 (no-skill) path, so Intelligence matters for every class on every chest
- `chestLockRolled`'s emitted `need` field reflects the intel-adjusted threshold, making the change directly observable in the event log and testable
- `characterSheetViewModel` (`src/browser/viewModels.js`) surfaces the same `intelBonus(c)` value as a new `lockBonus` field on the INTELLIGENCE stats row — sheet and engine consume the identical helper, so they cannot drift (mirrors the existing `damageBracket`↔`weaponDamage` sync pattern)
- New unit test in `test/unit/encounters.test.js` proves, for the identical rng sequence, a low-Intelligence character fails a borderline lock roll (need stays 8) while a high-Intelligence character succeeds (need rises to 10)
- Logged as a `// DELIBERATE RULES CHANGE (04.1-04, 2026-09-09, RULE-01)` comment in both `derived.js` and `encounters.js`, per the project's fidelity-rule precedent (`engine/movement.js:239`)
- Confirmed via full test suite: **no rng draw was added, removed, or reordered** — the bonus only changes the comparison (`need`), so `openChest`'s `rng.d(10)`/`rng.d(20)` lock-roll draw and every subsequent `gainWilmst`/scroll/treasure draw stay in the exact same sequence

## RNG-Safety Confirmation (critical acceptance criterion)

`intelBonus(c)` is a pure function of `c.intel` with zero rng access. It is added to `need` — a plain number computed BEFORE `rng.d(10)`/`rng.d(20)` is called — never to the roll result and never inserted as its own draw. Both `openChest` code paths were changed identically:

```js
// tiered path
const need = [0, 5, 7, 8][Math.min(tier, 3)] + intelBonus(c);
const roll = rng.d(10);          // unchanged draw, unchanged position
opened = roll <= need;

// bare-d20 path
const need = 8 + intelBonus(c);
const roll = rng.d(20);          // unchanged draw, unchanged position
opened = roll <= need;
```

No chargen RNG order was touched. `npm test`'s full suite — including `test/parity/chargen-parity.test.js` (byte-compares chargen RNG order) and `test/determinism/same-seed-same-result.test.js` — passed at 511/511, confirming determinism/parity are unaffected.

## Decisions Made

- Chose the curve `clamp(floor((c.intel - 10) / 5), 0, 2)` — a simple, easily-audited threshold/step/cap triple, documented inline, that yields a bonus large enough to matter (a high-INT bare-d20 roller goes from a 40% chance to open a chest to a 50% chance) without trivializing locks.
- Surfaced the sheet read as an additive `lockBonus` field rather than reformatting the existing `value` string, to avoid any risk to `characterSheetViewModel.test.js`'s exact-value assertion on the INTELLIGENCE row and to keep the raw `c.intel` score visible unchanged.
- Left `mazeworld.html` untouched — this plan's declared `files_modified` scope (and the phase's file-ownership map) puts the DOM-rendering pass for the new `lockBonus` field in a later UI-focused plan; `characterSheetViewModel` already exposes the value for that pass to bind to.
