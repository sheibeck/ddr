# Phase 04.1 Plan 05: Darkness Persistent State + Darkness-Phobia Freeze Summary

**Wired the "Darkness" encounter-table result to a real persistent per-character darkness counter (`c.darkFor`) that shrinks fog-of-war and applies in-dark combat penalties even off a dark tile, and made Darkness-phobic characters freeze on an in-dark encounter start — both mitigated by Hardiness, both fully deterministic, `npm test` 522/522 green.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 2/2 completed
- **Files modified:** 13 (6 engine/narration files, 2 unit test files, 5 parity-suite files needed to accommodate the new chargen field)

## Accomplishments

- **Persistent darkness state (Task 1).** `engine/character.js`'s `rollCharacter` now initializes `c.darkFor = 0` (a plain assignment — no chargen rng added). `engine/encounters.js`'s `fallDark` (the handler the "Darkness" content-table result already dispatched to, per `encounterDot`'s switch) now sets `c.darkFor = 30` (a documented `DARKNESS_DURATION` constant) in addition to its existing 4-tile-radius paint — this is the previously-inert table effect the CONTEXT flagged, now wired.
- **Single-hook generalization.** `engine/derived.js`'s `inDark(state)` was extended to `tileDark || c.darkFor > 0`. Because `revealRadius`, `toHit`, `foeToHitVs`, and `combat.js`'s `combatInDark`/no-crit-in-dark checks all already call `inDark(state)` rather than reading `.dark` directly, every one of them automatically honors the persistent state — and every existing Night Vision waiver keeps working unchanged, since those waivers wrap `inDark()` too.
- **Per-step lifecycle.** `engine/movement.js`'s per-step tick block (alongside the existing affliction/haste/invis/ether decrements) now decrements `c.darkFor` and clears it at zero, pushing a narrated `darknessLifted` event (`src/browser/eventNarration.js`: "The dark loosens its grip. You can see again.").
- **Darkness-phobia freeze (Task 2).** `engine/combat.js`'s `startCombat` phobia-freeze condition was generalized from `c.phobiaType === type` to `(c.phobiaType === type || (c.phobia === "Darkness" && inDark(state)))`, still gated by the same `!(Hardiness && rng.d(2)===1)` mitigation and the same `frozen`/`shookOffFrozen` seam the 5 type-matched phobias use. The two operands are provably mutually exclusive per character (Darkness's `phobiaType` is always `null` in the `PHOBIAS` catalog), so no character can double-trigger the freeze or double-roll the Hardiness mitigation, and the `&&` short-circuit means the new `rng.d(2)` draw only ever fires for a Darkness-phobic character who is actually in the dark and has Hardiness — never during chargen, never for anyone else.
- **12 new tests** (6 in `movement.test.js`, 6 in `combat.test.js`) directly proving: fallDark sets the counter and it drives `inDark`/`revealRadius` off a dark tile; Night Vision waives the shrink; the counter decrements and clears with a `darknessLifted` event; a Darkness-phobic character freezes when dark (via tile OR the persistent counter) but not when lit; Hardiness's 50% mitigation both succeeds and fails correctly; and a non-Darkness phobic character never freezes or draws extra rng.
- **Full suite: 511/511 → 522/522 green**, including parity/determinism/roundtrip.

## Decisions Made

- **Field name/value:** `c.darkFor` (steps remaining), matching the plan's suggested name; duration constant `DARKNESS_DURATION = 30` steps, documented at its declaration in `engine/encounters.js`.
- **inDark generalization over per-consumer patching:** confirmed via `read_first` that `revealRadius`/`toHit`/`foeToHitVs`/combat's in-dark checks all already route through `inDark(state)`, so extending that one function was sufficient — no other file needed a parallel "is darkness active" check.
- **Freeze condition, not freeze mechanism:** the Darkness-phobia freeze reuses `state.combat.frozen`/`shookOffFrozen` verbatim; only the *trigger condition* was generalized, per the plan's explicit instruction not to invent a new freeze mechanism.
- **Reused `phobiaFrozen` narration** rather than adding a Darkness-specific event type — the plan permitted either; reuse was the lower-risk choice (no new `formatEventsCoverage` entry to maintain, and the existing line ["Your phobia has you rooted to the spot."] reads fine for any phobia).
- **darknessFell event payload gained a `duration` field.** Additive change, not a rename — `formatEventsCoverage.test.js` and every existing consumer of `darknessFell` still work unchanged (extra fields are ignored by narration builders' `??`/`?.` defensiveness).
