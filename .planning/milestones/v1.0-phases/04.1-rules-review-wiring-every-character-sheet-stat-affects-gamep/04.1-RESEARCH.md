# Phase 04.1: Rules Review & Wiring - Research

**Researched:** 2026-09-09
**Domain:** Rules audit / wiring (deterministic engine + content tables + browser presentation) for "Delve, Die, Repeat"
**Confidence:** HIGH (this is a closed, fully-readable codebase — every claim below is `file:line` evidence, not external research)

## Summary

This is a code-audit phase, not a research-the-ecosystem phase. There is no external library to evaluate — the deliverable is a systematic READ of `engine/*.js`, `content/*.js`, `src/browser/*.js`, and `mazeworld.html` to answer one question per character-sheet field: **does gameplay actually consult this number, or is it decoration?**

The headline finding: **the engine is far more thoroughly wired than the phase's premise assumes.** Of the 8 HERO-sheet stat rows plus Win Potential, Rations, and Gold, only **Intelligence** is a true cosmetic orphan (rolled at chargen, displayed, never read again by any engine function on the player's own character — only a *foe's* `intel` field is read, for spell resistance). Every Fighter special skill (12/12) and 8 of 9 Thief special skills are wired into real resolution; the one gap (Sewing) is disabled by a pre-existing dead-code bug the team already flagged and deliberately preserved (movement.js:216-220). Phobias already have a partial combat effect (freeze-in-place) for 4 of the 10 rolled phobias; the other 6 (including the two most common — Darkness and Death) do nothing. The single genuinely confusing subsystem is the **store food purchase → Win Potential → Rations** chain: every food item, regardless of its `wp` value (2 to 15), converts to exactly +1 ration, a 1:1 mapping the player never sees explained anywhere in the UI.

**Primary recommendation:** This phase is 80% "confirm and rename," not "build new systems." Wire Intelligence into ONE existing check (spell resistance is the obvious symmetric hook — the engine already resists spells cast AT an intelligent target, but nothing lets the player's own Intelligence resist anything cast at them, or gate any Thief/skill check). Fix the Sewing/Master-of-Arms dead-code bug (`c.dr` is read but never set — trivial one-line fix, restores an entire class of gameplay to two subclasses/skills). Decouple food purchases from ration count (rations should be their own store line item). Rename "skill points" → "experience points" and "Win Potential" → "Hit Points" as a pure text/label pass (the underlying state fields `c.sp`/`c.wp`/`c.maxWP` should NOT be renamed — 9 engine files and the parity/determinism/save-shape test suite key off those exact identifiers). Give the 6 no-op phobias a real effect using the SAME `frozen`-on-encounter-start hook the 4 working phobias already use, generalized from "combat type" to "trigger condition" (darkness → freeze on `inDark`, heights → climb/leap penalty, etc. — user must choose the mapping, see Section 7).

## Project Constraints (from CLAUDE.md)

- **Fidelity rule:** "The prototype's rules are canon; deviations must be deliberate design decisions, not accidental regressions." This governs the whole phase — every "fix" below must be logged as a deliberate rules change (the codebase already has a precedent comment style for this: see `engine/movement.js:239-248`'s "DELIBERATE RULES CHANGE (04-DR12...)" block; new changes from this phase should follow the same pattern).
- **Rules engine decoupling:** "Must remain decoupled from UI and fully serializable," "zero direct DOM reads/writes inside the rules engine functions." Any new wiring (e.g., a phobia effect, a rations-economy rewrite) MUST live in `engine/*.js` as a pure `(state, rng, events) → events` function, never in `mazeworld.html`'s DOM-touching code.
- **Determinism:** No `Math.random()`, only the injected seeded rng; RNG consumption order must be preserved exactly where parity/determinism tests depend on it (`test/parity/chargen-parity.test.js`, `test/determinism/same-seed-same-result.test.js`).
- **Tone:** dark-but-family-friendly deadpan sarcasm — any new narration strings (phobia effects, rations-economy messaging, renamed labels) must match `content/flavor.js` / `src/browser/eventNarration.js`'s existing voice.
- **No new SDKs/deps:** this is a pure logic/content/wiring phase; nothing here should need a new package.

The HUD (`.mw-hud-hp-lab`, `mazeworld.html:1209`) **already** shows `HP <b>0</b>/<b>0</b>` — the top-of-screen HUD was renamed to "HP" at some point (likely during a prior mobile-UX pass) but the HERO character-sheet panel (`mazeworld.html:1288`, `Win Potential`) was NOT updated to match. **This means the app currently shows the player two different names for the same stat depending which screen they're on** — itself a pre-existing bug this phase should close, not just a stylistic choice.

### The food/rations tangle — actual current behavior

1. **Store stock generation** (`engine/economy.js:85`): `for (const f of [FOODS[0], FOODS[1], FOODS[5]]) add(\`${f.n} (+${f.wp} wp)\`, f.cost, "eatRation", { wp: f.wp });` — three of the six `content/foods.js` entries (Chicken +12wp, Bread +5wp, Meat +15wp) are offered; the store-row LABEL STRING ITSELF is built inside the engine (not a browser template), embedding "wp" directly into serialized `state.store.stock[i].n`. **This is a rename-risk site distinct from ordinary UI text** — the string lives in engine-generated state, not a static label.
2. **Purchase effect** (`engine/economy.js:39-43`, `STORE_EFFECTS.eatRation`): `c.wp = Math.min(c.maxWP, c.wp + params.wp); c.rations++;` — **every** food purchase, regardless of its `wp` value, adds exactly **+1 ration**, no matter whether the food gave 5 wp or 15 wp. Bread (5 wp, 15 gold) and Meat (15 wp, 25 gold) both yield "+1 ration" — the ration gain has zero relationship to the wp gain or the price paid.
3. **The player is never told this.** The store row reads e.g. "Chicken (+12 wp)" — the ration increment is a silent side effect, visible only after the fact via the HUD's rations counter or, in combat's parallel "cooked" mechanic (`engine/combat.js:345-354`), an explicit `cooked` event narrated as "+X wp, +1 ration."
4. **A second, independent food-find path exists**: `engine/encounters.js:256-263` (`findFood`, a random dungeon-tile encounter) draws a random `FOODS[d6]` entry and applies the identical `wp += f.wp; rations++` pattern — so the same "any food = +1 ration" rule is duplicated in two places (`economy.js` and `encounters.js`), both would need updating together if the ration-acquisition rule changes.
5. **This confirms the user's diagnosis exactly**: rations are conceptually a food-supply stat that should be bought/found as their OWN resource, but currently every acquisition path piggybacks a flat +1 ration onto a Win-Potential-restoring purchase with no visible or scaled relationship between the two.

**Provenance/risk split — this is the most important distinction for the planner:**
- **SAFE (display-text-only) renames:** every occurrence in `mazeworld.html` static markup, `content/flavor.js`, `content/epitaphs.js`, `src/browser/eventNarration.js`, and the `label:` strings in `src/browser/viewModels.js`'s `stats` array. These are pure presentation strings; changing them does not touch `state` shape, save files, or any test that compares state.
- **RISKIER (engine-generated string) rename:** `engine/economy.js:85`'s stock-label template embeds "wp" into a string that becomes part of `state.store.stock[i].n` — a value that gets serialized. Renaming the text there is still just a string change (not a schema change), but it IS engine code, not browser code, and any snapshot/fixture test asserting exact store-row text (check `test/unit/economy.test.js`) will need updating in the same commit.
- **DO NOT RENAME (state field / event-type identifiers):** `c.sp`, `c.wp`, `c.maxWP`, `c.rations`, event types like `spGained`/`healed`/`struck`/`foeKilled` (which carry `spGained`/`amount` fields, not renamed keys). These are read by ~9 engine files, the full `test/parity/*`, `test/determinism/*`, and `test/roundtrip/serialize-rehydrate.test.js` suites, and any existing save file on a player's device. Renaming these is a **save-migration-class change**, categorically different from a label rename, and should be explicitly declared IN SCOPE or OUT OF SCOPE by the user (Section 7) rather than assumed.

## Phobias / Quirks

**Generation:** A phobia is rolled once at character creation — `character.js:141,151`: `const ph = PHOBIAS[rng.d(10) - 1]; ... phobia: ph.n, phobiaType: ph.t`. It can also be RE-rolled later by two content triggers: a permanent-affliction roll (`content/afflictions.js:13-14`, two of the eight `AFFLICTIONS` rows are `phobia: true`, resolved by `engine/encounters.js:393-410` `catchAffliction`) and a dedicated "Phobia" dungeon-tile encounter-table result (`engine/encounters.js:434-442`, `newPhobia`). Both re-roll paths call the identical `PHOBIAS[rng.d(10) - 1]` draw.

**Full catalog** (`content/flavor.js:17-22`, 10 entries):

| Phobia (`n`) | Combat-type trigger (`t`) | Currently has a game effect? |
|---|---|---|
| Darkness | `null` | **No** |
| Death | `null` | **No** |
| Being trapped | `null` | **No** |
| Bodies of water | `null` | **No** |
| Bats and rats | `"Beasts"` | **Yes** |
| Vampires and the undead | `"Walking Dead"` | **Yes** |
| Heights | `null` | **No** |
| Fire | `"Demons"` | **Yes** |
| Sorcery | `"Magical"` | **Yes** |
| Crowds | `"Humans"` | **Yes** |

**The one existing mechanical hook:** `engine/combat.js:192-195` (inside `startCombat`): `if (c.phobiaType === type && !(skill(c, "Hardiness") && rng.d(2) === 1)) { state.combat.frozen = true; events.push({ type: "phobiaFrozen" }); }` — when the encounter's `ENC_TYPES` category (`content/bestiary.js:107`: `Beasts`/`Demons`/`Humans`/`Lair Beasts`/`Magical`/`Walking Dead`) matches the character's `phobiaType`, the player's first action that combat is consumed shaking off the freeze (`combat.js:219-224`, `shookOffFrozen`) instead of acting. The Fighter special skill "Hardiness" (`content/skills.js:13`: "−3 to all damage taken; phobias halved") gives a 50% chance to shrug it off entirely — this text is accurate and matches the code exactly.

**6 of 10 phobias (60%) — including the two most commonly-rolled-sounding, Darkness and Death — are pure flavor text with `phobiaType: null` and never trigger `phobiaFrozen` or anything else.** This is the concrete gap behind the phase's "make sure phobias have a game effect" directive.

**Existing systems a phobia effect could hook into** (so no new subsystem needs inventing):
- **The `frozen`/`shookOffFrozen` combat-freeze hook already exists** (`combat.js:192-195,219-224`) — trivially extensible to non-`ENC_TYPES` triggers by generalizing the CONDITION (not the effect): e.g. Darkness could freeze on `inDark(state)` at encounter start instead of on `type` match; Being trapped could freeze on a `climb`/`gorge`/one-way-door tile.
- **`toHit`/`foeToHitVs` modifier stacks** (`derived.js:71-83,100-112`) already read `eff(c, "toHit")` and similar item-effect keys — a phobia could apply a temporary combat-scoped penalty the same way an item effect does, without a new field type.
- **The affliction system** (`c.affliction`, `AFFLICTIONS` content table, `movement.js:123-134` per-step tick) is a ready-made "ongoing negative effect with a duration" pattern — Bodies of water or Heights (movement-triggered fears) could plug into a similar step/tile-triggered check rather than the combat-only freeze.
- **The Fighter skill "Hardiness"'s "phobias halved" clause is CODE, not just flavor** (`combat.js:193`) — any new phobia effect should respect the same Hardiness 50%-mitigation pattern for consistency, since that's the established design language.
- **Death (as a phobia) is thematically adjacent to the death-related SPELL kind `"death"`** (`magic.js:303-315`) and to `die()`/`epitaphFor` (`death.js:90-112`) but there is no existing "near-death" state hook (e.g., low-wp threshold) in the engine today to attach a Death-phobia effect to without inventing one.

**Rulebook note:** `mazeworld.pdf` (the 1994 tabletop rulebook) exists at the repo root but per the project's fidelity rule the prototype (`mazeworld.html`, and now the extracted engine) is canon and supersedes it — this research did not open the PDF, and the planner should not treat it as an authority for what phobias "should" do; that is a product decision for Section 7, not a rules-lookup exercise.

## Scrolls

**Current model, confirmed from `engine/magic.js:398-419` (`readScroll`) and `engine/economy.js:59-61`/`content/character.js:155`:**
- Scrolls are an **undifferentiated count** — `c.scrolls` is a plain integer, incremented by buying one at the store (`economy.js:60`, flat 900 gold, Magic Users only), finding one in a chest (`encounters.js:127-129`, a d6≥3 chance), or the misc-magic table (`encounters.js:315-317`), and Magic Users start with 1 (`character.js:155`).
- **Reading is gated by `canRead(state)`** (`magic.js:385-389`): a Pilfer can NEVER read scrolls (thematically consistent — "cannot use a single magic item that doesn't heal," `flavor.js:50`); everyone else needs to either BE a Magic User or carry the **Runes/Signs** Fighter skill ("read scrolls; without it they are waste paper" — this flavor text is literally true: a non-caster without the skill can hold scrolls but `readScroll` is a no-op guarded by `canRead`).
- **On use, `readScroll` draws ONE random spell** from `SPELLS.filter(sp => sp.lvl <= min(5, floor.depth + 1))` (depth-capped level, `magic.js:402-403`) — the player has NO CHOICE of which spell a scroll contains; it's purely random per-read, not fixed-per-item.
- **Outcome branches on caster status, not on any property of the scroll itself**: if the reader is a Magic User who can learn that school (`canLearn`), hasn't already learned it, and meets the level requirement, the spell is copied straight into `c.grimoire` for permanent use (`magic.js:406-409`). Otherwise it's cast immediately and for free — bypassing the caster's own spell-charge economy (`c.spellsUsed` is saved/reset/restored around the call, `magic.js:412-417`) and bypassing grimoire/level/school gates via the `c.scrollCast = true` flag that `castSpell` checks at `magic.js:55`.
- **This means the SAME scroll roll can do two very different things** depending entirely on who reads it: a Magic User might permanently gain a new spell; a Fighter with Runes/Signs gets a one-shot free cast of whatever the dice pick (which could be a combat-only offensive spell, a self-buff, or something situationally useless outside combat like `reveal`/`foresee`).

**What a scroll type-system (distinguishing combat-usable vs. grimoire-adding scrolls) would require** — scoped, not designed, per the task's "capture scope, don't over-design" instruction:
- A new `kind`/`school`/pre-rolled-`spell` field on each scroll INSTANCE (currently scrolls are a bare integer count, not objects — this is the biggest structural change: `c.scrolls` would need to become an array of scroll objects, similar to how `c.items`/`c.grimoire` already are arrays, likely touching `character.js`'s chargen, `economy.js`'s purchase effect, `encounters.js`'s two find-a-scroll paths, `magic.js`'s `readScroll`, and every UI surface that currently just prints the integer count (`mazeworld.html:2736` kit row, HUD).
- A decision on WHEN the spell is determined: at acquisition (roll-on-pickup, so the player can see "you found a Freeze scroll" and choose whether to carry/use it) vs. the current roll-on-read (a surprise every time). This is a real design fork, not an implementation detail — flagged as an open question in Section 7.
- Given the scope of touching 5 files' worth of `c.scrolls`-as-integer assumptions, this is almost certainly a LOWER-PRIORITY, possibly deferred-to-a-later-phase item relative to the Intelligence/phobia/rations/Sewing fixes, which are each 1-3 file changes.

## Existing Systems Inventory (for wiring)

Reusable infrastructure the planner should wire NEW rules THROUGH, rather than inventing parallel mechanisms:

- **Dice/check resolver:** `engine/dice.js`'s `rollDice(rng, {n,sides,bonus})` — every roll in the engine goes through this against plain dice-notation objects (content tables never contain closures — a hard project-wide rule, see `content/misc-tables.js`'s header comment). Any new roll (a phobia check, a rations-economy roll) must use this, not raw `rng.d(n)` math inline, when the notation is data-table-driven; `rng.d(n)`/`rng.pick`/`rng.shuffle` (from `engine/rng.js`'s mulberry32 wrapper) are fine for inline one-off rolls (that's the prevailing pattern throughout `combat.js`/`magic.js`).
- **The typed event system:** every state mutation pushes a `{type, ...fields}` object onto the caller-supplied `events` array (`engine/events.js` defines the handful of shared constructors like `moved`/`floorChanged`/`won`/`leveled`; most modules push inline object literals directly). `src/browser/eventNarration.js`'s `EVENT_NARRATION` table is the SOLE place a new event type's display string is added, and `test/unit/formatEventsCoverage.test.js` will fail the build if a new event type has no narration entry — this is a built-in guardrail the planner should rely on, not route around.
- **The affliction/status system:** `c.affliction = { kind, loss, per, left }`, ticked in `movement.js:123-134` on every step, cured by resting (`movement.js:209-212`). This is the ready-made pattern for anything "ongoing, periodic, curable by rest" — a strong candidate for a movement/tile-triggered phobia effect (e.g., Bodies-of-water, Being-trapped) rather than inventing a new field shape.
- **The combat-scoped modifier flags:** `state.combat.frozen`, `.weakened`, `.foeToHitPenalty`, `.inspired` — all read by `foeTurn`/`playerStrike` (`combat.js`) and settable by any module that has a live `state.combat` (spells already do this from `magic.js`). This is the seam the existing 4 phobias use and the seam the other 6 should extend through for combat-triggered effects.
- **Derived-stat computation:** `engine/derived.js` is the SINGLE place every displayed/consumed number (`toHit`, `strikeDie`, `weaponDamage`, `foeToHitVs`, `upkeep`, `eff`) is computed from `c`/`state`. Any new Intelligence-based check should be added here as a new exported function (or a modifier folded into an existing one, e.g. `foeToHitVs`) so the character sheet's `viewModels.js` and the combat engine automatically stay in sync (the same pattern that already keeps `damageBracket` in `viewModels.js` byte-identical to `weaponDamage` in `derived.js`).
- **Item effects (`eff(c, key)`):** `derived.js:24-28` sums an `eff[key]` across `c.items` — a generic, reusable "any carried item can nudge any named modifier" mechanism already used for `sight`/`toHit`/`dmg`/`foeToHit`/`upkeep`/`charges`/`greed`/`throw`/`spellDmg`. A phobia OR an Intelligence-based effect could reuse this exact key-lookup pattern instead of adding bespoke `if` branches, if the design calls for a numeric modifier rather than a binary freeze.

## Design Decisions Needed (open questions for the user)

These require product judgment this research cannot resolve from code alone. I will take these to the user before the planner locks a plan.

1. **What concrete game effect should each of the 6 currently-inert phobias have?**
   The 4 working phobias all use the SAME mechanism (freeze on encounter start when the foe-type matches). The 6 inert ones (Darkness, Death, Being trapped, Bodies of water, Heights) don't have an obvious matching "encounter type" — they're each tied to a SITUATION, not a monster category.
   - **Option A — generalize the freeze mechanic to situational triggers:** Darkness freezes when `inDark(state)` is true at encounter start (reuses the existing `combat.frozen` flag verbatim); Heights/Being-trapped apply a roll penalty on `climb`/`gorge` tiles (extends `movement.js`'s existing climb-check math); Bodies of water has no current "water tile" concept in the maze generator, so it may need to piggyback on drowning-adjacent flavor (e.g., treat it as a rare affliction-tick trigger) or be the ONE phobia left as flavor-only by explicit decision; Death could apply the "frozen" treatment when the player's own `wp` drops below some threshold (a near-death panic), a genuinely new trigger condition.
   - **Option B — give every phobia a uniform, situation-agnostic penalty** instead of situational freezing: e.g., ALL phobias apply a flat combat-to-hit or damage-taken penalty for the character's whole run, with no trigger condition needed (simpler to implement, but discards the existing 4-phobia "freeze when you meet what you fear" flavor and would need those 4 rewritten too, for consistency).
   - **Option C — keep the existing 4 as-is, and give the other 6 a DIFFERENT (not "freeze") mechanical hook** each suited to its flavor (Darkness → a to-hit penalty via `inDark` and NOT the freeze — freeze is already "seeing the thing you fear," darkness is "not seeing anything," a different emotional beat), accepting more asymmetry across the catalog in exchange for flavor-appropriateness.

2. **How should the rations economy work once decoupled from the Win-Potential/food purchase?**
   - **Option A — sell rations directly as their own store line item** (e.g., "Rations ×1, 10 gold" alongside the existing food-that-restores-wp items), leaving the existing wp-restoring foods as PURE healing purchases with no ration side effect at all. This is the most literal reading of "rations should just be rations."
   - **Option B — keep a food→ration conversion but scale it to the food's `wp` value** (e.g., every 10 wp of food = 1 ration, rounded) instead of the current flat +1-per-purchase, preserving the "eating food replenishes your supplies" flavor while fixing the arithmetic disconnect.
   - **Option C — remove the ration side effect from store food entirely, and make rations ONLY acquirable via the existing dungeon-tile "Food" encounter result** (`encounters.js:256-263`) and combat's `Cooking`-skill/beast-carcass path (`combat.js:345-354`), i.e. rations become a foraging-only resource, never a store purchase.
   Each option also implies a different fate for `engine/encounters.js:256-263`'s `findFood` (currently identical logic to the store's `eatRation`, would need the same decoupling applied in parallel if Option A or B is chosen).

3. **What is this phase's scope for the scroll type-system — full rework, partial, or deferred?**
   - **Option A — defer entirely.** The current "undifferentiated count, random spell on read" model is internally consistent (matches the tabletop-adjacent "unroll a mystery scroll" flavor) and touches no orphaned character-sheet stat; nothing in the phase's stated end goal ("if you see information on your character sheet that impacts gameplay, it should impact gameplay") is violated by scrolls today — the "Scrolls" kit row already does what it says.
   - **Option B — small fix only:** keep scrolls as a bare count, but let the player see/choose WHICH spell a scroll contains at read-time (or acquisition-time) via a lightweight roll-then-preview step, without restructuring `c.scrolls` into an array of typed objects.
   - **Option C — full rework:** `c.scrolls` becomes an array of `{spell, kind}` scroll instances rolled at acquisition (as scoped in Section 5), enabling a genuine "combat-usable vs. grimoire-adding" distinction the player can see before choosing to read one. This is the largest single line-item in this whole phase if chosen (5+ files, a save-shape change).

4. **Should `c.intel` (Intelligence) gain a mechanical read, and if so, where?**
   Not explicitly asked by the user's design brief but directly implied by "if you see information on your character sheet that reads like it impacts your gameplay, it should impact your gameplay" — Intelligence is the single clearest violation of that principle on the whole sheet.
   - **Option A — symmetric spell resistance:** the engine already resists spells cast BY the player AT an intelligent foe (`magic.js:86-96`); mirror it so foes casting offensive spells at the player check the player's OWN `c.intel` the same way, via a new resistance check inside the "thrown"/status spell-kind branches in `magic.js` (foes don't currently cast at all — `castSpell` is only ever invoked by the player; wiring foe-cast spells is a LARGER change than a simple resistance check, so this option may need to be paired with, or deferred until, foes gain offensive spellcasting).
   - **Option B — gate a Thief/skill-adjacent check:** e.g., a high-Intelligence bonus to `openChest`'s lock roll or `castSpell`'s Apprentice-backfire chance — smaller, self-contained, no dependency on foes casting spells.
   - **Option C — leave Intelligence as flavor, and note in the character sheet that it's a "roleplay" stat** (contradicts the phase's stated end goal, but is a legitimate scope-reduction the user may prefer given the size of Option A).
