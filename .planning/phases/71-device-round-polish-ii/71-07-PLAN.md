<objective>
Make the UI tap sound play only on a real press (POLISH-10, D-15). The plan folds in the source todo `.planning/todos/pending/2026-09-23-ui-tap-sound-plays-when-scrolling-over-a-button.md`, and the SUMMARY must name it. Moving that todo to `.planning/todos/done/` is the orchestrator's job after merge (D-13). This plan does not move it.

Purpose: on the Pixel 7, starting a scroll with a finger on any button (gear rows, board rows, the Oracle, sheets) plays the UI click. The cause is that the shell plays `playUiTap()` from a capture-phase `pointerdown` listener on `document`. That fires when the finger lands, before the browser knows whether the gesture is a tap or a scroll. D-15 changes this:
- the audio unlock stays on `pointerdown`;
- the tap sound moves to a capture-phase `click` listener, and a scroll never fires click;
- disabled, locked and guard-swallowed presses are silent;
- a long press is silent;
- the no-double-sound rule is kept.

Output:
- a pure `src/browser/uiTap.js` (the decision and the one-sound-per-press deferral);
- `sfxClipCount()` in sfx.js;
- the shell wiring (the guard registry in guardTap, `window.__mzTapArmed`, and the listener split);
- the tests;
- section M rows in docs/UAT-v2.0.md.

Planner rulings (record in the SUMMARY):
- **R-24: the inputGuards.js arm/settle question (D-15 asks the planner to decide).**
  - *The arm guard.* The shell can tell, so the sound follows the guard. guardTap records each element it wraps in a `tapGuards` WeakMap, with the same predicate its onclick checks (`encArmed`). The tap sound asks that predicate at click time. That is the same task, so it gets the same answer the handler gets.
  - *Why not the aria-disabled marker.* guardTap's marker is not a reliable "cannot act" signal. paintConditions rebuilds the condition chips on every paint, and guardTap re-stamps `aria-disabled="true"` on each one. The arm sweep only clears `#enc-panel`, `#mw-rail` and `.mw-legend-sheet`, never `#mm-conditions`. A plain "silent when aria-disabled" rule would therefore silence every condition chip for good. So a guarded element is judged by its guard. An element guardTap does not wrap is judged by its `aria-disabled` and `disabled` (the gear sheet's greyed `data-off` rows, the ☰ menu's disabled rows).
  - *The settle guard.* `DISMISS_SETTLE_MS` gates only `window.move` (the map canvas and keys), which never matches a button, so there is nothing for the sound to follow.
- **R-25: the skip tap is silent.** While `window.__mzBeat.active()` is true, a tap on a button inside `#enc-panel` is D-06's skip. Phase 58's `beatHurryTap` catches it, and the skip never acts, so it makes no tap sound. That covers a foe card, the 71-05 strip and 71-04's Details button (all guardTap-wrapped, and `encArmed()` is false mid-beat), plus any unguarded button in the panel. A locked action is silent twice over: `data-locked`, and `pointer-events:none`, which sends the tap to `#cb-act`, which is not a button.
- **R-26: one sound per press.**
  - *Today.* Every button ticks on pointerdown, even when its action then plays its own clip (GO DOWN plays the tick and then `stairs`; STRIKE plays the tick and then the first beat's `hit`). So today there is a double sound, and D-15's rule ("buttons that dispatch an action with their own clip don't also tick") is met by making it true.
  - *How.* The click listener decides eligibility in the capture phase, before any handler runs. It snapshots `sfxClipCount()` and whether a beat is active, then schedules one `setTimeout(…, 0)`. That task runs after every listener of that click has finished; a microtask would not, because microtasks run between listeners on a user-dispatched event. The tap plays only if no one-shot started and no round began in between.
  - *What counts.* The title theme's loop is not a one-shot and never counts. A clip that starts later than that task (for example a later beat line) is a new sound, not a second one for this press.
- **R-27: a long press.** 71-04's suppressor is a `window` capture-phase click listener, the first listener any click meets. After a fired long press, it calls `stopPropagation()` on the trailing click, so the `document` capture-phase tap listener never runs. Where Android fires no click after a long press, the result is silent too. This is pinned by listener order in the source and by a behaviour test that uses the real `createLongPress`.
- Keyboard and TalkBack activation (Enter/Space handlers calling `el.click()`, and TalkBack's double-tap) fire click and gain the sound. D-15 accepts this.
