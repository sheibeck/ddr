# Phase 91.2 Plan 06: The sign-in hold, requeue, sessions and the D-05 re-post Summary

Compete-ON runs are no longer lost to a missing Play Games sign-in: the queue holds them with no backoff, boardSync tells the shell the sign-in state and signs the player in on request, and the first named session on a device re-posts, once, the settled runs that never reached the board. Nothing was deployed and no live call was made.

## Behaviour

- **Hold (D-03, D-06).** A `signin` answer leaves the entry first with `attempts`, `failures` and `retryAt` untouched and persists nothing; the next flush after a sign-in posts it. Several deaths while signed out stay in order and all post after sign-in. Purge (Compete OFF) still discards held runs.
- **requeue.** Compete-gated, no network, one persist. Each valid summary whose hash is in `settled` and not already an entry leaves `settled` and re-enters the entries, with `versionOf(hash)` when valid, else `version`. Unknown, invalid or already-queued runs are skipped.
- **Sessions.** `session()` (quiet) and `signIn()` (interactive) share `runSession`: gated (Compete OFF answers `{ state: "off" }` with no identity or board call), never throw, call `onSession` once with a frozen `{ state, name }` (ok to signedIn, signin to signedOut, unavailable, offline, server or refused to error, off to off). On signedIn they run the D-05 re-post and then `flush({ force: true })`.
- **Hold reporting.** `flush()` and `record()` call `onSession({ state: "signedOut", name: null })` when the queue answers signin.
- **boot.** Compete ON runs `session()` instead of the bare flush; Compete OFF still makes no network call and no Play Games call.
- **D-05 re-post (T-91.2-22, -23, -24).** Eligible runs are stored runs (graveyard and bests, tolerant parse, hash re-verified by `collectBackfillRuns`) whose hash is in `queue.snapshot().settled`; those `client.ownRuns(uid)` already lists are dropped; the rest go through `queue.requeue` with the boot history's version for the hash, else the current version. The settled ledger only ever holds Compete-ON runs, so a Compete-OFF run is never eligible (pinned by a test). A failed `ownRuns` posts nothing and leaves the marker unset (retried next session). The marker `{ v: 1, done: true, count }` is written after a successful read, and a second session re-reads nothing and posts nothing (pinned).

## Deviations from Plan

None - plan executed exactly as written. Two small judgment calls inside the plan's latitude: (1) when no stored run is in the settled ledger the marker is written without a board read, because there is nothing to compare; (2) `client.clear()` is called before `ownRuns` so a stale 5-minute cache cannot hide a run that is missing from the board.

## Notes for later plans

- **91.2-07/08:** the shell wires `onSession` (account block: SIGN IN when `signedOut`, the name when `signedIn`) and calls `boardSync.signIn()` from the SIGN IN row. `session()` is safe to call on app resume; it is cheap when signed out (identity answers `signin` with no network call).
- `boardSync.boot({ history })` stores the history for the re-post's version lookup, so call `boot` before the first `session()`/`signIn()` for the best versions (a missing history just falls back to the current version).
- `ownRuns` pages at most 500 rows; a player with more than 500 board runs may see some re-posted, which the doc id answers as "exists".
