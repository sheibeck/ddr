<objective>
Build the pure, DOM-free presentation modules the Phase 34 combat screen consumes, plus their unit tests, before any `mazeworld.html` edit happens: the fight-log line/roll pipeline (CSCR-04), the four-action grid + submenu view-model (CSCR-05), and the foe-card / YOUR LOT / header / major-overlay view-models (CSCR-02, CSCR-03, CSCR-06 content). Wave 1 touches zero `mazeworld.html` lines so it can never conflict with the sequential shell waves.

**Decision 1 recorded here (RESEARCH Open Question 1 — fight-log roll detail sourcing):** extend `toastsForAction` non-destructively with `opts.withIdx` (Phase 32 `opts.limit` precedent) so each surviving folded entry keeps its `idx`/`type`, and derive the tap-reveal detail from `narrateEvent(events[idx])` via a new `oracleDetailText` export. Justification in one line: CONTEXT.md pins "log line count = folded count" (the `round-card-worst-case` retarget), so the folding/dedup pipeline must remain the ONE source — sourcing lines from raw `result.html` would yield one line per narrated event and break both that pin and the 400-seed fold proof. A folded multi-event entry reveals the dice of its FIRST constituent event (`events[idx]`); the Oracle stays the complete per-swing log (CSCR-04 "the Oracle stays the complete log"). The DR18 CSS rule scoping is an explicit task in Plan 02.

Purpose: every later plan wires DOM to these modules through `window.__mz*` bridges; testing the logic here (node --test, synthetic fixtures) means the shell plans only need source-assertion pins.
Output: `src/browser/toasts.js` (extended), `src/browser/fightLog.js`, `src/browser/combatMenu.js`, `src/browser/combatPanel.js`, three new test files.
</objective>
