Build the Play Console import zip tool, its validator and the docs, then build the real zip and hand it to the user together with a readable copy table.

Purpose: ROADMAP Phase 98 criteria 4 and 5 (ZIP-01, ZIP-02, ZIP-03). The zip is built by hand with Node built-ins only (project zero-SDK rule): a small zip writer using stored entries and `zlib.crc32`, a matching reader that the validator uses to re-read the file from its own bytes.

Output: the library, the CLI, three test files, the two docs, the `.gitignore` entry, the real zip (git-ignored) and the hand-off.
</objective>

<zip_format>
The byte layout the writer produces and the reader parses (all integers little-endian; verified during planning by writing a stored zip this way and reading it back with Python's zipfile, which reported no errors and the 1980-01-01 timestamp):
- Local file header, 30 bytes then the ASCII name then the data: signature 0x04034b50; version needed 10; flags 0; method 0 (stored); time 0; date 0x0021 (1980-01-01); crc32 of the data; compressed size; uncompressed size (both equal the data length); name length; extra length 0.
- Central directory header, 46 bytes then the name: signature 0x02014b50; version made by 20; version needed 10; flags 0; method 0; time 0; date 0x0021; crc32; compressed size; uncompressed size; name length; extra length 0; comment length 0; disk number 0; internal attributes 0; external attributes 0; offset of the local header; then the name.
- End of central directory, 22 bytes: signature 0x06054b50; disk 0; central directory disk 0; entries on this disk; total entries; central directory size; central directory offset; comment length 0.
The reader finds the end record by scanning back from the end of the buffer (at most 65557 bytes), reads the entry count and central directory offset, parses each central header, follows its offset to the local header (checking the signature, then data start = offset + 30 + local name length + local extra length), and returns each entry's name, flags, method, crc, sizes, DOS time and date, directory flag and data. Method 0 data is taken as is; method 8 data goes through zlib.inflateRawSync with `maxOutputLength` set to the per-file limit plus one so a bomb cannot expand; any other method, an encrypted flag (bit 0), a size or CRC mismatch (zlib.crc32), an offset outside the buffer or an unparseable record becomes an entry in a `problems` array instead of a throw. The reader never writes an entry to disk.
</zip_format>

<csv_format>
- AchievementsMetadata.csv, one row per achievement in listOrder: Name,Description,Incremental value,Steps Needed,Initial State,Points,List Order. An incremental entry writes `True` and its steps; a standard entry writes `False` and an empty Steps Needed field (two commas in a row). Initial State is Hidden or Revealed exactly. <validator_rules>
RULES is a frozen array of `{ id, catches }` in this order; validateZip returns `{ ok, violations: [{ rule, message }], stats }` with violations sorted by RULES order then entry or row order, where `stats` carries entries, achievements, points, incremental and hidden counts. Rules marked (house) go beyond Google's list and are labelled so in `catches`.
1. zip-readable: end record found, central directory parses, every entry readable, no unsupported method, no encryption, CRC and size match, offsets inside the buffer. Later rules that need entries are skipped when nothing is readable.
2. no-subdirectories: no entry name contains "/" or "\" and none is a directory entry (this also rejects ".." and absolute paths).
3. unique-file-names: no two entry names are equal ignoring case.
4. only-csv-png: every name ends in .csv or .png (case-insensitive) and the only CSV names are AchievementsMetadata.csv and AchievementsIconsMappings.csv (the optional localisations file is not used: the game is English only).
5. file-size: every entry's uncompressed size is strictly under 1000000 bytes.
6. file-count: at most 403 entries.
7. zip-size: the whole buffer is strictly under 800000000 bytes.
8. required-files: both CSVs are present once, and at least one PNG.
9. no-header-row: neither CSV starts with its column titles (case-insensitive "name," prefix).
10. csv-columns: every metadata row has exactly 7 values, every mapping row exactly 2, and no blank line sits inside a file (one trailing blank line is tolerated, a CR before the LF is tolerated on read).
11. incremental-spelling: column 3 is exactly True or False.
12. initial-state-spelling: column 5 is exactly Hidden or Revealed.
13. steps-rules: Steps Needed is empty exactly when column 3 is False; when True it is a digits-only integer from 1 to 10000.
14. points-rules: Points is a digits-only integer, a multiple of 5, from 5 to 200.
15. list-order-rules: List Order is a digits-only integer above zero, unique, and ascending down the file (house).
16. name-rules: a name is 1 to 100 characters and unique (compared exactly and ignoring case).
17. description-rules: a description is 1 to 500 characters (the 1 is house: every achievement carries a description).
18. text-charset: name and description are printable ASCII (0x20 to 0x7E) and contain no double quote (house).
19. points-total: the sum of Points is at most 2000, Play's game cap.
20. achievement-count: from 1 to 400 rows, Play's lifetime cap per game.
21. mapping-matches-metadata: every mapping name equals exactly one metadata name and every metadata name has exactly one mapping row.
22. icon-exists: every mapped icon file name is an entry in the zip.
23. icon-unique-and-used: no icon file is mapped by two rows and no PNG in the zip is left unmapped (house).
24. icon-png-512: every PNG has the 8-byte PNG signature, an IHDR chunk first, and width and height of exactly 512.
25. matches-catalog (only when a catalog is passed): the rows equal the catalog in count, order, name, description, type, steps, initial state, points, list order and icon basename.
`validateZip(buffer, { catalog, limits })`: `limits` overrides LIMITS entries for tests (for example a small zip-size or achievement cap).
</validator_rules>

<cli_spec>

`node tools/achievements-zip.mjs --copy-table [--out <file>] [--root <dir>]`: print the markdown copy table to stdout, or write it to <file>.
Exactly one of --build, --check, --copy-table; zero, two or an unknown flag, or a flag missing its value, prints the usage line and exits 2. Exit 1 is a build or validation failure. Use process.exitCode, not process.exit, so output is never cut short.
</cli_spec>

<copy_table_spec>
copyTable(catalog) returns markdown: a `# Achievement copy table` heading; a line saying it is generated by `node tools/achievements-zip.mjs --copy-table --out docs/ACHIEVEMENTS-COPY.md` and must not be edited by hand; a totals line (count, points and the headroom under Play's 2000-point cap, incremental, standard and Hidden counts, all computed); a short note that the Description column is Play's copy and freezes when the zip is imported while the Line column is the in-game unlock line and can be reworded later; then one section per block of COPY_BLOCKS, each `## <n>. <title> (<size>)` and a table with the columns `#`, `Name`, `Description (Play)`, `Line (in game)`, `Pts`, `Type`, `Steps`, `Starts`, `Reveals` (`#` is the list position, Steps is the number or a dash, Reveals lists the revealed achievements' names or a dash); then `## Reveal pairs` with a table of `Revealer`, `Its line (the hint)`, `Reveals` for each of the 8 pairs. Output uses LF only and ends with one trailing newline, so it is deterministic.
</copy_table_spec>
