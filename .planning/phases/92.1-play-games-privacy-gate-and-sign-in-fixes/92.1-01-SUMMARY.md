# Phase 92.1 Plan 01: Play Games privacy gate and sign-in fixes Summary

The bundled Play Games SDK no longer signs the player in on a Compete-OFF launch: the manifest removes its auto-init provider, `MainActivity` starts it before `super.onCreate` only when stored Compete is not `false`, and a Compete turned ON mid-session starts it and signs in at once; the SIGN IN row hides when sign-in cannot work and a failed tap raises one plain rail card; a fresh install gets arrows.

## What was built

**1. Privacy gate (native).**
- `AndroidManifest.xml` declares `xmlns:tools` and `com.google.android.gms.games.provider.PlayGamesInitProvider` with `authorities="${applicationId}.playgamesinitprovider"` and `tools:node="remove"`. Checked against the real merged manifest (`app/build/intermediates/merged_manifests/debug/processDebugManifest`): zero `PlayGamesInitProvider` entries.
- `MainActivity.onCreate` calls `PlayIdentityPlugin.initSdkOnce(getApplicationContext())` before `super.onCreate`, only inside `competeIsOn(this)`. That helper reads SharedPreferences group `CapacitorStorage`, key `ddr.settings.v1`, parses with `org.json`, and is OFF only for an exact JSON `compete: false`. A missing, empty, non-string, unparsable or non-object blob, or any throw, is ON. It never logs.
- `PlayIdentityPlugin`: `private static boolean sdkInitialized` plus `static synchronized void initSdkOnce(Context)`; `ensureInit()` delegates to it, so the activity and the plugin share one initialize per process (the flag is raised only after `initialize` returns, so a failure can be retried). The header's lazy-init / A6 paragraph is replaced by an "INIT AND THE PRIVACY GATE" paragraph naming the two start points.
- Java compile check passed: `node tools/pin-jdk.mjs && node tools/gradle.mjs :app:compileDebugJavaWithJavac` (BUILD SUCCESSFUL, no APK built).
- Tests (`test/unit/android-system-bars.test.js`): the manifest provider removal, MainActivity's gated initialize before `super.onCreate` (comment-stripped, so prose cannot satisfy it; also pins the blob read, the "only `compete:false` is OFF" expression, the catch-returns-true, and no `Log` call), and the plugin's single idempotent init. The existing MainActivity pin was retitled; the retire-sweep scan needed no change (nothing it sweeps matches the new text).

**2. Compete ON mid-session.** `setCompete(true)` now runs the same interactive `board.signIn()` the row uses (state goes `busy`, the held-runs notice is marked moot, a tap during the prompt is ignored, and an answer that arrives after Compete went OFF changes nothing). `firebaseAuth.doSession(true)` calls the plugin `init` first (guarded for seams without it); an init failure resolves a plain reason with no prompt and no network. The quiet `session()` path never calls `init` (it only runs while Compete is ON, when the SDK is already up). The normal session/claim flow then runs unchanged inside `boardSync.signIn`.

**3. The sign-in row.**
- `identity.canSignIn()` returns `seamsReady()`; the account state carries `canSignIn` (true unless exactly false) and `accountSheetView` hides the row when it is false. The ☰ account block and the title sheet both draw `accountSheetView`, so one change covers both.
- A row tap or a toggle-ON sign-in that comes back `unavailable` raises one `signinUnavailable` card; `error` (or a rejection) raises one `signinFailed` card. Success, a dismissed prompt, offline and off raise none. Copy (in `ACCOUNT_COPY.cards`): "PLAY GAMES ISN'T HOME" / "THE SIGN-IN FELL OVER", family-friendly, tone dull, each saying the runs wait safe.
- Dormant config was tested only with an injected `playConfig` (empty `webClientId`); the shipped `firebaseConfig.js` was not touched.

**4. Fresh-install default.** A real `engineAdapter.boot` on empty storage writes `ddr.bests.v1` (and `ddr.runs.v1`) before `readSettings`; the old check counted that key, so a fresh install read `tap` (reproduced against the old file). `settings.js` now counts `ddr.bests.v1` only when it holds a run, a ranked board entry or a `last`, or is unreadable. Tests cover the real first boot, the exact empty record, and 2.2.0 upgrades (bests with runs, ranked-only, unreadable, empty bests plus graveyard, empty bests plus save, save alone, and a stored blob with and without `movement`).

## LISTING.md and in-game help re-read (lines ~94-95, 167-173, 225-226; `offHelp`)

True with the fix for what they describe, so nothing was edited:
- "Compete off: the SDK never starts" (and "never starts the Play Games SDK", "asks for no Play Games sign-in"): a cold launch with Compete OFF now starts nothing and signs in nothing.
- "the game starts the SDK only then [Compete on]": true.
- `offHelp` "Compete off means no Play Games sign-in": true for launches with Compete OFF.

One honest edge for the user to decide (not changed because `test/unit/store-listing.test.js` pins the exact phrase "Compete off: the SDK never starts"): a session that STARTED with Compete ON and is then switched OFF keeps the already-started SDK (and its sign-in) until the app process ends; the SDK cannot be un-initialized. Nothing reaches our backend, and the next launch with Compete OFF starts nothing. If the listing should say so, the wording and that test pin both need a one-clause change.
