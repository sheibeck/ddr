# Phase 92.1: Play Games privacy gate and sign-in fixes - Context

**Gathered:** 2026-10-02 (orchestrator, from the milestone-close device check C2 and a gsd-debugger diagnosis)
**Status:** Ready to execute (one plan, 92.1-01)

<domain>
## Phase Boundary

Inserted after Phase 92, at milestone close, before Release 2.3.0. It is a privacy-gate defect found on the Pixel 7 debug build: the bundled Play Games SDK signs the player in on every launch whatever the Compete setting says. It also fixes two small sign-in UX gaps and a first-launch settings bug found during the same diagnosis. Requirement: BOARD-31 (the privacy gate), plus the 91.2 Data safety promises in store-listing/LISTING.md.
</domain>

## Diagnosis (gsd-debugger, 2026-10-02, diagnose only)

- **Root cause.** `play-services-games-v2:22.1.0` merges its own `com.google.android.gms.games.provider.PlayGamesInitProvider` (initOrder 99) into the app manifest.
  - At process start it runs the same call as `PlayGamesSdk.initialize()`. That starts `AutomaticGamesAuthenticator`, which on MainActivity's `onActivityCreated` binds the games connect service, and GMS signs in silently.
  - Nothing reads Compete, so the plugin's lazy `ensureInit()` never matters.
  - Evidence: the packaged debug manifest; `dumpsys package` shows the provider registered; the logcat lines run from the connect-service bind before plugin registration, through `Successfully authorized`, to `signIn: Returning SUCCESS` and `shouldShowWelcomePopup` true.
- **Data leaving the device with Compete OFF.** Nothing reaches our backend. Google sees the sign-in, a player fetch, "Started a new game run" and recorded engagement on every launch. This makes LISTING.md lines 94-95 ("Compete off: the SDK never starts"), the in-game help ("Compete off means no Play Games sign-in") and the darktier-studio privacy pages untrue until fixed.
- **SDK behaviour (javap on the AAR).**
  - In the UNINITIALIZED state, `isAuthenticated()` and every API call return ApiException status 10 and never start authentication.
  - The automatic attempt fires only on an `onActivityCreated` seen AFTER initialize, so in this single-activity app initialize must run in `MainActivity.onCreate` BEFORE `super.onCreate`.
  - Google's PlayGamesSdk reference: `initialize()` is needed only when the provider is disabled, so removing it is the documented route.
- **The tap that "does nothing".** `signInTap` → `boardSync.signIn` → `doSession(true)` returns "unavailable" at `seamsReady()`, because `PLAY_GAMES_CONFIG.webClientId` is `""` (the console batch is still pending). The SIGN IN row stays visible in that state (`src/browser/account.js:144`), and a tap flips to "SIGNING IN…" and straight back.
- **The first-launch settings bug.** The first boot writes `ddr.bests.v1` before `readSettings` runs, and `EXISTING_INSTALL_KEYS` includes that key (`src/browser/settings.js` ~153, 192-199). A fresh install is therefore treated as an existing one and gets `movement:"tap"` instead of "arrows".
- Compete defaults ON on a fresh install (`SETTINGS_DEFAULTS.compete: true`, Phase 67 D-01). That is by design and unchanged. It is stored in Capacitor Preferences `ddr.settings.v1` (`shared_prefs/CapacitorStorage.xml`).

<decisions>
## User rulings (2026-10-02)

1. **Fix it now, before release.** Remove the SDK's auto-init provider (`tools:node="remove"`). Initialize the SDK in `MainActivity.onCreate` BEFORE `super.onCreate`, only when the stored settings say `compete !== false`; a missing or unreadable blob means the default, ON. Compete-ON cold boots keep today's silent sign-in.
2. **Compete turned ON mid-session: sign in right away.** The toggle-ON path initializes the SDK if needed and calls the interactive `signIn()`, then continues the normal session/claim flow. When the web client ID is empty (dormant config), it degrades exactly as rule 3 says.
3. **The sign-in row: hide it and say why.** Hide the SIGN IN row (menu account block and title sheet) while sign-in cannot work (`seamsReady()` false, the dormant config). When a tap comes back unavailable or error, raise ONE rail card with a plain reason (event + EVENT_NARRATION + rail twin per the gates).
4. **Movement default: fix it.** A fresh install starts on "arrows". The existing-install detection must not count keys the first boot itself writes before `readSettings` (for example `ddr.bests.v1`). Upgrades from 2.2.0 keep their stored or legacy choice.

### Gates (milestone, unchanged)
- Greenfield. Every new event gets an EVENT_NARRATION entry plus a rail twin, and `node tools/narrative-review.mjs --check` must pass.
