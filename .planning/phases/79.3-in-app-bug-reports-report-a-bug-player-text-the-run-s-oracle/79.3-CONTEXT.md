# Phase 79.3: In-app bug reports: Context

**Gathered:** 2026-09-28 (user request and two AskUserQuestion rulings in the v2.1 autonomous run)
**Status:** Ready for planning

<domain>
## Phase Boundary

Players can report a bug from inside the game. A REPORT A BUG row in the ☰ menu opens a report sheet. The player types what happened and taps Send. The report, with the current run's Oracle attached, is written to the game's Firebase project (Firestore). A scheduled GitHub Action in `sheibeck/ddr` files each new report as a public GitHub issue and marks it filed.

**Not in scope:**
- screenshots or attachments;
- a save-state snapshot;
- an in-app list of past reports;
- replies to the player;
- crash auto-reporting;
- Firebase Cloud Functions, the Firebase JS SDK, and App Check. Revisit App Check only if spam appears.

The user's request (verbatim, 2026-09-28): "we have one final thing to do before this build is done. I want a way for my users to submit bugs. Add a report bug link in the dropdown from the user menu. It should let them type out what happened. Then when they submit, it should attach the oracle and submit it as an issue in the github repository for this rpo."
</domain>

<decisions>
## Implementation Decisions

### Transport (user ruling 2026-09-28: "Firestore + GitHub Action")
- **D-01:** The app writes each report to **Firestore in the existing Firebase project `delve-die-repeat-6ba5f`**, the game's own project, used for its OAuth. Billing is **off** (the Spark plan), so:
  - no Cloud Functions;
  - the project can never be billed.
  - The user asked to "leverage firebase instead of cloudflare to keep this whole project organized".
- **D-02:** A **scheduled GitHub Action in sheibeck/ddr** reads new reports from Firestore and files each one as an issue with the workflow's built-in `GITHUB_TOKEN` (`permissions: issues: write`).
  - No GitHub token exists anywhere outside GitHub.
  - The Action reaches Firestore with a **Firestore-only service account key**, stored as a repo secret.
- **D-03:** The app talks to Firestore through **plain `fetch` to the Firestore REST API**, with no Firebase JS SDK. It POSTs to `https://firestore.googleapis.com/v1/projects/delve-die-repeat-6ba5f/databases/(default)/documents/bugReports?key=<API key>`, with the body in Firestore's typed-value JSON (`{ fields: { text: { stringValue } ... } }`).
  - The API key is a **dedicated Google API key restricted to the Firestore API**. It is a public identifier, not a secret; the orchestrator provisions it.
  - The key and project id live in one small config module. Planner's choice of path, e.g. `src/browser/bugReportConfig.js`.
- **D-04:** **The game still runs fully offline.** Reporting is the only network path the player starts. There is no background sending and no queue. If a send can't reach the network, the sheet keeps the draft and says so, and the player retries when they have signal.

### Visibility (user ruling 2026-09-28: "Public, with a notice")
- **D-05:** Issues are filed **publicly on sheibeck/ddr**, as the user asked.
- **D-06:** Before Send, the sheet states plainly that the report and the run's Oracle **will be posted publicly on GitHub**, and that the player should not include anything private. This is plain fact, not a joke; the house voice can follow it.
- **D-07:** No account or Play Games identity is sent: no player id, email or avatar. The hero's generated name appears only because it is in the Oracle.

### Entry point and sheet
- **D-08:** Add a new **REPORT A BUG** row to the ☰ dropdown (`#mw-hud-menu`). It sits after SETTINGS and before the split line that starts the quit rows (SAVE & QUIT, ABANDON).
  - It is **enabled on every screen**: the map, combat and every encounter, all five tabs, the Oracle, and while dead. hudMenuRowStates must never disable it.
  - The menu's own glyph rule applies: mock-style glyphs are allowed only in this menu, and the planner picks one.
  - The row needs its own id and handler. The four legacy chip ids are the routing for the existing rows; don't rename them.
- **D-09:** The report sheet follows the house sheet pattern. See the Settings sheet (`src/browser/settings.js` and the shell's `openSettingsSheet`) and the other sheets. It has:
  - a title;
  - a multi-line text box, required, with a max length of about 2,000 characters and a visible counter near the limit;
  - the public notice (D-06);
  - Send and Cancel.

  Its states:
  - **idle**, with Send disabled until there is text;
  - **sending**, with the controls locked;
  - **sent**, with a short thank-you in the house voice; then the sheet closes and the draft clears;
  - **failed**, where the draft is kept, the message says what happened (offline vs server refusal), and Send stays available to retry.

  The Android back button closes the sheet, per the existing back-button handling. The draft survives closing and reopening the sheet within a session (in memory is enough).
- **D-10:** The sheet opening or closing must not touch the game state (`S`). Reporting is shell-only. It must not pause, advance or save the run beyond what opening any sheet already does.

### Report contents
- **D-11:** Each report (one Firestore document) holds:
  - `schema: 1`
  - `status: "new"`
  - `text`: the player's words, trimmed
  - `oracle`: the run's Oracle as **plain text, oldest line first**. The Oracle is the DOM log `#log`, filled by the shell's `logLine(html)`: newest first, capped at 160 `<p>` entries, and **not in `S`**. Strip the HTML to text, and keep the roll spans' text. Cap it at a size well inside Firestore's 1 MiB document limit, e.g. 100,000 characters, keeping the newest lines if it must trim.
  - `oracleLines`: the count
  - `version`: the stamped `versionName (versionCode)` from `#mw-app-version`. `tools/build-www.mjs` stamps it into www/index.html, and the dev loop shows a placeholder.
  - `platform` / `device`: `navigator.userAgent`, trimmed, plus the Capacitor platform if available
  - `run`: a small map of the run context read from `S`, only if a run exists: floor depth, hero class, sub-class, race and level, the step or turn count, and alive or dead
  - `clientTime`: an ISO string. It is informational only; the Action trusts the document's server `createTime`.
- **D-12:** Pure and testable. Building the payload means Oracle extraction, trimming, the size caps and the Firestore typed-value encoding. It is a pure, DOM-free module taking plain inputs. The send function takes an injected `fetch` and a timeout of about 15 s. The shell only gathers inputs and renders the states.

### Firestore rules (D-13)
- `firebase/firestore.rules` (with `firebase.json` and `.firebaserc` pointing at `delve-die-repeat-6ba5f`) allows ONLY `create` on `bugReports/{id}` when:
  - the keys are exactly the D-11 set: `hasOnly` for all of them, plus `hasAll` for the required ones;
  - each field has its type;
  - the sizes are bounded: text 1–2,000; oracle ≤ 100,000; version ≤ 64; device ≤ 400; the run map has only its known keys;
  - `status == "new"` and `schema == 1`.
- No `get`, `list`, `update` or `delete` for clients, and every other path is denied.
- The Action's service account bypasses the rules; it is IAM, not rules.

### The Action (D-14)
- **Where it lives:** `.github/workflows/bug-reports.yml`.
  - It runs on a schedule (`*/15 * * * *`) and by hand (`workflow_dispatch`).
  - `permissions: { issues: write, contents: read }`, and a `concurrency` group so runs never overlap.
  - It runs `node tools/bug-reports/file-issues.mjs` on Node 22 with **zero npm installs**.
- **Auth:** the script signs a service-account JWT with `node:crypto` (RS256), exchanges it at `oauth2.googleapis.com/token` for a `datastore` access token, and uses the Firestore REST API (`runQuery` and `patch`).
- **Secret:** `FIREBASE_BUG_REPORTS_SA` holds the service account JSON. `GITHUB_TOKEN` comes from the workflow, and `GITHUB_REPOSITORY` gives the target.
- **Per run:** file at most about 20 reports, oldest `createTime` first.
- **Idempotency:**
  1. Flip `status` from `"new"` to `"filing"`, with the document's `updateTime` as a precondition.
  2. Create the issue. Its body carries a hidden marker, `<!-- ddr-report:<docId> -->`.
  3. Patch `status: "filed"`, `issueNumber` and `issueUrl`.
  - A report stuck in `"filing"` for over 10 minutes (the run died in between) is reconciled by searching recent `player-report` issues for its marker. If found, mark it filed; if not, file it.
  - A report is never filed twice.
- **Label:** the issue is labelled `player-report`. Create the label if it's missing, and ignore a 422.
- **Issue format:**
  - Title: `[Player report] <first line of the text, ≤ 70 chars>`.
  - Body, in order:
    1. the player's text as a blockquote, with **@mentions and #refs neutralised** (e.g. a zero-width joiner after `@` and `#`);
    2. a small details table: version, device, floor, hero, level, turn, sent at (the server `createTime`) and the Firestore doc id;
    3. the Oracle in `<details><summary>Oracle (N lines)</summary>` inside a code fence that its content can't break out of (a longer fence, or escaped backticks).
  - Stay under GitHub's 65,536-character body limit by trimming the Oracle's **oldest** lines, with a note that the full Oracle is in the Firestore doc.
- **Tests:** the formatter and the runner are pure or take an injected `fetch` and clock. Unit-test them: neutralising, fence-safety, trimming to the limit, the idempotency paths, the stale-filing reconcile, and the label-exists 422.
- **Operations note (docs):** GitHub disables scheduled workflows in a public repo after 60 days with no repo activity. Reports wait safely in Firestore until the workflow is re-enabled in the Actions tab.

### Copy and ledgers (D-15)
- Every new player-facing line follows the house voice: the fact first, then the joke, family-friendly. This covers the row label, the sheet title, the notice, the placeholder, the button labels, and the sending, sent and failed lines.
- Each line gets a row in a why-ledger JSON under `docs/narrative-pass/why/`, with a name sorting after the existing ones, e.g. `q-260928-z5-bug.json`.
- Run `node tools/voice-inventory.mjs --check-ledgers --after --coverage` (0 errors), and regenerate the review page with `node tools/narrative-review.mjs --md --html`.

### Play compliance (D-16)
- `store-listing/LISTING.md`'s Data safety answers change from "no data collected" for this path:
  - **App activity → Other user-generated content** (the report text) and **App info and performance → Diagnostics** (the Oracle, version, device);
  - collected, optional, user-initiated, encrypted in transit;
  - deletion on request through the existing delete-data URL.
- Also draft the paragraph the darktierstudios.com privacy policy (https://darktierstudios.com/privacy/apps) needs: bug reports are sent only when the player taps Send, they are posted publicly on GitHub, and they are deletable on request.
- The user makes the Play Console and website changes at milestone close. Put both on the close checklist.

### Provisioning and the live test (D-17: the orchestrator, not an executor)
- The orchestrator, with the user's firebase, gcloud and gh logins (authorized by the user's ruling), does these:
  1. Enable the Firestore API and create the `(default)` database in Native mode (location `nam5`).
  2. Deploy `firebase/firestore.rules`.
  3. Create the Firestore-restricted API key.
  4. Create the `ddr-bug-reports` service account with `roles/datastore.user`, and a key. Set it as the `FIREBASE_BUG_REPORTS_SA` repo secret with `gh secret set`, then delete the local key file.
  5. Create the `player-report` label.
  6. After the code is on master and pushed, run the live end-to-end test: send one clearly-marked test report, dispatch the workflow, see the issue appear, then close it with a note.
- Plans must leave clear hooks for this, such as a `firebase.json` the CLI can deploy and a script entry to send a test report. They must not require an executor to hold credentials.

### Claude's Discretion

- Whether the test-report sender is a `tools/` script or a `--dry-run` / `--send-test` flag on the filer.
</decisions>

<specifics>
## Specific Ideas
- GitHub issue body limit: 65,536 characters. Firestore document limit: 1 MiB, and a string field under that.
- Firestore REST create: `POST …/documents/bugReports?key=KEY` with the body `{ "fields": { … } }`. A 403 or PERMISSION_DENIED from the rules means a refused payload. Show it as a failure; never crash.
- The Action's reads use `runQuery` with `where status == "new"` (and a second query for stale `"filing"`). Use `patch` with `updateMask.fieldPaths` and `currentDocument.updateTime` for the lock.
- Keep the whole path free of new npm dependencies, in the app and in the Action.
</specifics>

## Deferred Ideas
- App Check (Play Integrity), to prove reports come from the real app. It needs a native plugin; revisit only if spam appears.
- Attaching a save-state snapshot, kept only in Firestore and not in the public issue, for exact replays.
- An in-app "your reports" list or replies.
</deferred>

## Addendum: in-game patch notes (NOTES-01, NOTES-02)

The user's rulings: "In v2.1, before the build (Recommended)" and "Once per update (Recommended)". The user's request: "Whenever we build a new version for deploying to google play store, that should come with a detailed set of patch notes. Make it human readable, but break it down clearly … categorizing and organizing notes together … put these patch notes into github and tag the version. Then we can link to the patch notes from the player menu".

- **D-18: the source.** There is one Markdown file per release, `docs/patch-notes/<versionName>.md`, with these categories in fixed order (empty ones dropped):
  1. a headline
  2. Classes (per class, then per sub-class)
  3. Races
  4. Abilities & spells
  5. Items & gear
  6. Monsters & difficulty
  7. Interface
  8. Bug fixes

  Each entry reads old → new in plain words.
  - The orchestrator writes the 2.1.0 content with the user before the release build. This phase ships the pipeline plus a placeholder `docs/patch-notes/2.1.0.md` that follows the format.
  - The format is documented in `docs/patch-notes/README.md`.
- **D-19: bundled in the app.** `tools/build-www.mjs` bundles the notes file for the version in `android/version.properties` into www (as a JS or JSON module; the planner decides). The dev loop reads the same file.
  - The build **fails** if the current version has no notes file. This is the release-gate hook.
- **D-20: the in-game view.**
  - A **PATCH NOTES** row in the ☰ menu sits next to REPORT A BUG and is always enabled.
  - It opens a sheet in the house sheet pattern, showing the current version's notes rendered from a minimal, pure, dependency-free Markdown subset (headings, bullets, bold, links).
  - The sheet has a "Past versions on GitHub" link to https://github.com/sheibeck/ddr/releases, which opens in the system browser.
- **D-21: auto-show once per update.**
  - On the first launch where the stamped version differs from the last-seen version, stored in the app's durable storage (the existing storage module, not raw localStorage), the sheet opens once after the title or boot settles. It must never pop over a live fight.
  - A fresh install marks the version seen without showing the notes, since there is nothing to update from. The planner confirms this reading; the alternative is to show it on a fresh install too.
- **D-22: the other outputs.** `tools/patch-notes.mjs` (or similar) prints:
  - the GitHub Release body, for `gh release create v<versionName> --notes-file`;
  - a ≤ 500-character Play "What's new" cut from the headline plus the top bullets, and it errors if the cut exceeds 500 characters.

  `docs/RELEASING.md` gains the step. The orchestrator runs the GitHub Release at the release (tag `v2.1.0`).
- **Copy.** The row label, sheet title and link text get why-ledger rows, like D-15. The notes body itself is release content, not ledgered UI copy.
</addendum>
