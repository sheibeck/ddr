## Summary

This is a pure infrastructure phase with no gameplay-visible change. It has two independent halves, both prerequisites the milestone's `README`/`STATE.md` "Engine gate" makes non-negotiable: (1) enumerate exactly which `content/bestiary.js` creatures the five parity-fixture scenarios that actually roll a foe (`combat.win`, `combat.lose`, `combat.flee`, `combat.parley`, `magic.cast-damage`) draw, so Phase 18's bestiary rebalance knows precisely which creatures need a narrow `comparables.js` carve-out and which are free to change; and (2) extract `pickFoeTarget` and `applyFoeDamageToPlayer` out of `foeTurn` (`engine/combat.js:819-990`) as named, tested, byte-identical-behavior helpers so Phase 19's foe-ability resolver can reuse the melee path instead of re-implementing ward/armor/damage logic a second time.

I ran the actual enumeration (not just proposed it) using the existing harness (`test/parity/harness/comparables.js#applyStartCombat` + `engine/engine.js#newRun`) and got a concrete, surprising-in-its-narrowness result: **every parity-fixture-exercised foe is a LEVEL-1 creature** (because every fixture starts a level-1 character on floor 1, and `startCombat`'s `maxLvl = clamp(min(c.level, depth), 1, 5)` clamps to 1). The exposed roster is exactly four creature names across two types: `Bat/Rat`, `Shriek`, `Viper` (Beasts, level 1) and `Dante` (Humans, level 1). Every other creature in the entire bestiary — every level 2-5 entry, every Demons/Lair Beasts/Magical/Walking Dead entry — is completely unconstrained by the frozen parity suite and can be freely rebalanced in Phase 18 with zero carve-out risk.

For the refactor half, the risk is entirely about preserving RNG draw order and the early-return-on-death control flow: `foeTurn`'s hero-damage branch calls `die(state, ...)` and `return events` the instant `c.wp <= 0`, which skips every remaining foe in the loop AND the end-of-turn `c.ward`/`c.mirror` decrement — any extraction must preserve this exactly, which means the new helper cannot itself decide to `return` from `foeTurn`; it must signal the outcome back to the caller.

**Primary recommendation:** Extract `pickFoeTarget(state, rng)` and `applyFoeDamageToPlayer(state, foe, dmg, roll, rng, events)` as new named exports inside `engine/combat.js` (not a new file — Phase 19's `engine/foeAbilities.js` will import them from here), keep the simplified member-damage branch (`combat.js:867-889`) entirely separate and untouched, have `applyFoeDamageToPlayer` return a small `{ onArmour, died }` result object so `foeTurn` preserves its exact `continue`/`return events` control flow, and add a `test/unit/foe-turn-draw-count.test.js` using a counting-rng wrapper that pins the exact number of `.d()`/`.pick()` calls a fixture-representative fight consumes today — this is the baseline Phase 19 re-runs to prove its ability-attempt gate adds zero draws for foes without an `abilities` field.

### Pattern 1: Extract `pickFoeTarget` — preserve the exact zero-draw gate

**What:** Replace the inline block at `engine/combat.js:860-865` with a call to a new exported function.

**Current inline code (verbatim, for exact-behavior reference):**
```js
// engine/combat.js:860-865 (current)
const liveMembers = C.allies ? C.allies.filter((a) => a.wp > 0) : [];
let member = null;
if (liveMembers.length) {
  const pick = rng.d(liveMembers.length + 1);
  if (pick > 1) member = liveMembers[pick - 2];
}
```

**Recommended extraction:**
```js
// engine/combat.js — NEW export
/**
 * pickFoeTarget(state, rng) — chooses which live combatant a foe's swing
 * targets: null means the hero, a member object means that party member.
 * DETERMINISM GATE (unchanged from the inline version this replaces,
 * combat.js:860-865): the `rng.d(pool)` roll is drawn ONLY when at least one
 * live party member exists. Empty/absent party ⇒ zero draws, `null` returned
 * immediately — byte-identical to every solo parity fixture today.
 */
export function pickFoeTarget(state, rng) {
  const C = state.combat;
  const liveMembers = C.allies ? C.allies.filter((a) => a.wp > 0) : [];
  if (!liveMembers.length) return null;
  const pick = rng.d(liveMembers.length + 1);
  return pick > 1 ? liveMembers[pick - 2] : null;
}
```

Call site inside `foeTurn`'s swing loop becomes `const member = pickFoeTarget(state, rng);` — identical draw count, identical draw order, identical return semantics (`null` = hero).

**Trade-off:** None — pure extraction, no behavior change. This is also exactly the seam Phase 19's foe abilities need (`bolt`/`drain` ability kinds target the same pool), per `.planning/research/ARCHITECTURE.md`'s Pattern 4.

### Pattern 2: Extract `applyFoeDamageToPlayer` — preserve the early-return-on-death control flow

**What:** Replace `engine/combat.js:901-981` (dmg computation stays split — see below) with a call to a new exported function that returns a small result object so `foeTurn` can preserve its exact `continue`/`return events` shape.

**Line-by-line source of truth (verified by direct read, `engine/combat.js:892-981`):**
- `892-899`: to-hit die + roll + miss check — **stays inline in `foeTurn`** (not part of the extraction; CONTEXT.md scopes the helper to the damage pipeline, not to-hit resolution).
- `901-904`: raw dmg computation (`f.lvl² + sp.dmg or rng.d(6)`), `C.weakened` halving, critical doubling (`roll===1` or Soldier crit-on-2), **Hardiness reduction** — dmg/roll computation with its RNG draw stays inline (the value must exist before the helper can be called with a `dmg` parameter), but **Hardiness reduction moves INTO the helper** per CONTEXT.md's explicit list.
- `906-917`: `c.halfNext` (Pendant of Fortitude) — moves into the helper.
- `919-939`: ward absorb/reflect/shatter, including the `killFoe(...); continue;` branch when a reflected blow kills the foe — moves into the helper.
- `940`: `if (dmg <= 0) continue;` — moves into the helper (as an internal early-return, not a `continue` — see result-object design below).
- `942-963`: armor-soak roll (`rng.d(20)`, gated on `av.wp>0 && av.ar>0 && !ignores`) — moves into the helper.
- `964-977`: `wp -= dmg`, `struckByFoe` event push — moves into the helper.
- `978-981`: `die(state, ...)` call + `return events` — the `die()` call moves into the helper; the `return events` signal must propagate back to `foeTurn` via the result object (the helper cannot itself `return` from `foeTurn`).

**Recommended signature and shape:**
```js
// engine/combat.js — NEW export
/**
 * applyFoeDamageToPlayer(state, foe, dmg, roll, rng, events) — the hero-
 * damage pipeline a landed foe swing runs through: Hardiness reduction,
 * c.halfNext (Pendant of Fortitude, single-charge), ward absorb/reflect/
 * shatter, armor soak (rng.d(20) via armorSoak(c), gated), the struckByFoe
 * event, and die() on lethal. Ports engine/combat.js's inline hero-damage
 * branch (formerly lines 901-981) verbatim, draw-for-draw.
 *
 * Returns { onArmour, died }: `onArmour` true means the caller's swing loop
 * should `continue` to the next swing (no wp lost); `died` true means the
 * caller (foeTurn) MUST `return events` immediately — do not process any
 * remaining foes or the end-of-turn ward/mirror decrement, exactly matching
 * today's early-return-on-death behavior.
 */
export function applyFoeDamageToPlayer(state, foe, dmg, roll, rng, events) {
  const c = state.c;
  const f = foe;
  if (skill(c, "Hardiness")) dmg = Math.max(1, dmg - 3);
  if (c.halfNext) {
    dmg = Math.ceil(dmg / 2);
    c.halfNext = false;
    events.push({ type: "damageHalved", name: f.name });
  }
  let warded = 0;
  if (c.ward && c.ward.pool > 0) {
    warded = Math.min(c.ward.pool, dmg);
    c.ward.pool -= warded;
    dmg -= warded;
    if (c.ward.reflect && warded > 0) {
      f.wp -= warded;
      events.push({ type: "wardReflected", target: f.name, amount: warded });
      if (f.wp <= 0) {
        killFoe(state, f, rng, events);
        return { onArmour: false, died: false }; // "continue" — foe died to reflect, not the hero
      }
    } else if (warded > 0) {
      events.push({ type: "wardAbsorbed", amount: warded, remaining: c.ward.pool });
    }
    if (c.ward.pool <= 0) {
      events.push({ type: "wardShattered" });
      c.ward = null;
    }
  }
  if (dmg <= 0) return { onArmour: false, died: false };

  let onArmour = false, blocked = 0;
  const ignores = f.sp && f.sp.noArmor;
  const av = armorSoak(c);
  if (av.wp > 0 && av.ar > 0 && !ignores) {
    const soak = rng.d(20);
    if (soak <= av.ar) {
      onArmour = true;
      blocked = dmg;
      if (!av.magic && dmg > av.min) c.armorWP = Math.max(0, c.armorWP - dmg);
      dmg = 0;
      if (!av.magic && c.armorWP <= 0) events.push({ type: "armorDestroyed" });
    }
  }
  if (onArmour) {
    events.push({ type: "armorSoaked", name: f.name, amount: blocked });
    return { onArmour: true, died: false };
  }
  c.wp -= dmg;
  events.push({ type: "struckByFoe", name: f.name, roll, need: undefined /* caller already knows `need`; see note below */, dmg, ignoresArmor: !!ignores, critical: roll === 1 });
  if (c.wp <= 0) {
    die(state, "combat", f.name, rng, events);
    return { onArmour: false, died: true };
  }
  return { onArmour: false, died: false };
}
```

Call site inside `foeTurn` becomes:
```js
const result = applyFoeDamageToPlayer(state, f, dmg, roll, rng, events);
if (result.onArmour) continue;
if (result.died) return events;
```

**Note on the `struckByFoe` event's `need` field:** the current inline code has `need` in scope at the point the event is pushed (`combat.js:973`). Since the helper doesn't receive `need` in the signature above, either (a) pass `need` as an additional parameter (`applyFoeDamageToPlayer(state, foe, dmg, roll, need, rng, events)`), or (b) have `foeTurn` push the `struckByFoe` event itself using the helper's returned `dmg`. **Recommend (a)** — it's a trivial signature addition and keeps the event-shape assertion (`struckByFoe`'s exact fields) unchanged, satisfying the "zero output change" requirement more directly than reshaping which function pushes the event.

**Trade-off:** A `{ onArmour, died }` result-object return is slightly more ceremony than a bare `continue`/`return`, but it's the only way to preserve `foeTurn`'s exact control-flow shape (skip remaining foes + skip the ward/mirror tick on death) without duplicating that shape inside the helper itself (which would require the helper to know about `foeTurn`'s outer loop, breaking the single-responsibility boundary CONTEXT.md asks for).

**The member branch stays untouched and separate** (`combat.js:867-889`) — CONTEXT.md's decision explicitly allows sharing via a mode flag but does not require it; the member branch has no ward/armor/Hardiness/halfNext at all (per its own header comment, `combat.js:867-869`), so forcing it through the same helper adds branching complexity for zero correctness benefit in this phase. Leave the unification question to Phase 19 if it ever wants it (per `.planning/research/PITFALLS.md` Pitfall 16 — don't assume parity between the two paths without a stated design reason).

### Anti-Patterns to Avoid

- **Making `applyFoeDamageToPlayer` itself `return events` on death:** it doesn't have access to `foeTurn`'s outer `events` return contract in a way that lets it skip `foeTurn`'s OWN remaining code (the ward/mirror decrement after the loop) — only `foeTurn` can `return events` early. The helper must signal via its return value, never attempt the early-return itself.
- **Collapsing the member branch and hero branch into one function "for consistency":** the member branch is deliberately simplified (no ward/armor/mirror/Hardiness, no `die()`) — per `.planning/research/PITFALLS.md` Pitfall 16, this asymmetry is intentional, not an oversight to "fix" during a behavior-preserving refactor.
- **Reordering the raw-dmg computation (weakened halving, critical doubling) into the helper:** these depend on `roll` and `C.weakened`, which are to-hit/swing-scoped concepts computed just before the helper is called; moving them in changes nothing functionally but blurs the boundary CONTEXT.md drew ("Hardiness onward" is the helper's scope) — keep the split exactly as scoped above so a future reviewer can line up the helper's code against CONTEXT.md's decision list 1:1.

## Common Pitfalls

### Pitfall 1: Reordering the extraction breaks the ward-reflect-kills-foe short-circuit
**What goes wrong:** The ward-reflect branch (`combat.js:925-931`) can kill the FOE (not the player) and `continue`s to the next swing — this is a different outcome than the player dying, and a naive extraction might conflate "the helper resolved something lethal" with "the player died," accidentally returning `{ died: true }` for a foe's own reflect-death and causing `foeTurn` to `return events` when it should instead just move to the next swing.
**Why it happens:** Both paths call `killFoe`/`die`-adjacent functions and both are "something died" — but only the PLAYER's death (`c.wp <= 0`) should trigger `foeTurn`'s early return.
**How to avoid:** The result object's `died` field must be set ONLY at the `c.wp <= 0` branch (the very last check in the helper), never at the ward-reflect `f.wp <= 0` branch (which returns `{ onArmour: false, died: false }` and lets the caller `continue`, exactly as shown in Pattern 2's code above).
**Warning signs:** A parity fixture where a ward-reflect kill happens mid-fight suddenly stops processing the rest of that foe's swings/the rest of the foe list.

### Pitfall 2: `state.combat` becomes `null` after `die()` — don't read `C`/`state.combat` again inside or after the helper on the death path
**What goes wrong:** `die()` (`engine/death.js:90-112`) sets `state.combat = null` unconditionally. If `foeTurn`'s loop (or the helper) reads `state.combat`/`C` again after calling the helper on the path where `died: true`, it will hit `null` and throw or silently no-op in a confusing way.
**How to avoid:** The `if (result.died) return events;` check must be the FIRST thing `foeTurn` does after calling the helper — no other `C.*` reads on that path, mirroring the current code's `return events` being the literal next statement after `die()` (`combat.js:979-981`).

### Pitfall 3: The parity suite's `combatComparable` strips `rngState` — it doesn't itself prove "zero extra draws" numerically
**What goes wrong:** It's tempting to treat "full parity suite green" as sufficient proof for FID-02. But `combatComparable`/`movementComparable`/`economyComparable` (`test/parity/harness/comparables.js:146,184,282`) all destructure `rngState` OUT of the compared state (the frozen prototype's `S` has no `rngState` field at all to compare against). The parity suite proves draw-order correctness only INDIRECTLY — an extra/missing draw desyncs every subsequent roll, which then shows up as a diverging `wp`/`foe` value on the NEXT compared action. It is a real, load-bearing guard, but it is not literally a draw-counter.
**How to avoid:** FID-02 needs a DEDICATED test that counts draws directly (Pattern below), not a reliance on "the parity suite would have caught it." State this explicitly in the phase's verification notes so the planner doesn't substitute one for the other.

### Pitfall 4: This phase must NOT need any `comparables.js` changes — treat any need for one as a signal the refactor changed behavior
**What goes wrong:** Unlike Phase 18/19, this phase introduces zero new serialized fields (no new `f.*`/`c.*` keys) and zero new event types. If implementing the extraction seems to require a new carve-out in `combatComparable`, that is a strong signal the refactor is NOT behavior-preserving — stop and re-check the extraction against Pattern 1/2 above rather than adding a carve-out to make tests pass.
**Warning signs:** Any edit to `test/parity/harness/comparables.js` during this phase's implementation.

### Draw-count regression test (FID-02) — counting-rng wrapper

```js
// test/unit/foe-turn-draw-count.test.js
// Source: engine/rng.js (direct read) — makeRng's public surface is exactly
// {d, pick, shuffle, next, getState, setState}; wrapping the 4 draw-producing
// methods gives an exact, auditable draw count with no dependency on
// mulberry32's internal step arithmetic.
import test from "node:test";
import assert from "node:assert/strict";
import { makeRng } from "../../engine/rng.js";
import { foeTurn } from "../../engine/combat.js";

function countingRng(seed) {
  const inner = makeRng(seed);
  let draws = 0;
  return {
    d: (n) => { draws++; return inner.d(n); },
    pick: (a) => { draws++; return inner.pick(a); },
    shuffle: (a) => { draws += Math.max(0, a.length - 1); return inner.shuffle(a); },
    next: () => { draws++; return inner.next(); },
    getState: inner.getState,
    setState: inner.setState,
    get draws() { return draws; },
  };
}

test("FID-02: a foe with no `abilities` field draws EXACTLY today's expected count — 1 to-hit + 1 dmg roll, no more", () => {
  // fixedState/fixedFighter/fixedFloor/fixedFoe/fixedCombat helpers — reuse
  // test/unit/party-combat.test.js's exact shapes (no party, single foe, no
  // acid/ward/armor) so only the swing's to-hit + dmg draws are possible.
  const rng = countingRng(42);
  const state = /* fixedState({ combat: fixedCombat([fixedFoe()]) }) */ null; // see test/unit/party-combat.test.js for the real helper
  foeTurn(state, rng, []);
  assert.equal(rng.draws, 2, "exactly the to-hit roll + the d6 damage roll — no ability-attempt roll exists yet, and none should be drawn for a foe lacking `abilities`");
});
```

**Phase 19 reuse note:** copy `countingRng` verbatim into Phase 19's own ability-gate test, add `abilities: []` (empty array) to the same `fixedFoe()` and re-assert `rng.draws === 2` (still zero extra draws — an empty abilities array must behave identically to an absent one), then add a non-empty `abilities: ["boltFire"]` case and assert a HIGHER count only there.
