## Read before Task 1

**Re-read the landed code first.** Find every site by name; line numbers drift. Record BASE_58 = `git log --diff-filter=A --format=%H -- .planning/phases/58-motion-pacing/58-CONTEXT.md | tail -1`.

**The render path.** `engineCombatAction(type, extra)` in the module script calls `dispatchWithNarration`, which appends the round's lines to `window.__mzFightLog` (or, when combat ends, parks them on `window.__mzFightEnd`). It then sets the state, normalises the target, synthesises `lastStrike`, runs `noteCombat` (which may set `after.beats` or `window.__mzLootReport`), fires haptics, writes the Oracle lines, and finishes with `window.paint(); window.renderEncounter();`. The beat replaces only that final tail, and only when `planBeat` returns a plan. The runner's first line renders synchronously inside `start`, so the panel never shows a blank frame.

**Why the other branches need `!bv &&`.** For a combat-ending round, `S.combat` is already null and `S.dead`, `S.beats` or `S.pendingLoot` is already set, so without a guard `renderEncounter` would jump straight to the death card, over-panel or loot card. Prefixing those branch conditions with `!bv &&` lets the beat render the combat body (from the frame state) first; the settle render then takes the normal branch. For a mid-fight round, those branches are skipped anyway, because `S.combat` is set.

**Why the hurry listener is capture-phase on `#enc-panel`.** Every combat button is wired with `guardTap` (an `onclick`), and fight-log rows have their own `onclick`. A capture-phase listener on the panel runs before any of them, and `stopPropagation` there keeps the tap from ever reaching its target. The CSCR-08 tests forbid a tap-anywhere-to-DISMISS listener in the renderEncounter region. This listener is the locked D-11 exception: it never dismisses or acts, and it runs only while a beat is live. Re-pin those tests to name it exactly (Task 3), so it is a documented, tested exception rather than a regex blind spot.

**Harness.** The shell sandbox leaves `renderEncounter` real (only `draw`/`renderRail` are stubbed), but it does not wire `__mzFightLogVM` or `__mzCombatVM` (its comment says the snapshot surfaces never reach them). Wire both from the real modules, plus `__mzBeat` from a real `createBeatRunner`, and confirm `shell-tab-snapshots.test.js` is unchanged. `engineCombatAction` itself lives in the module script and cannot run in the sandbox. Tests reproduce its handoff (set the after-state, append the batch to the log, `planBeat`, `runner.start`), and a stripped-source anchor pins the real handoff.
