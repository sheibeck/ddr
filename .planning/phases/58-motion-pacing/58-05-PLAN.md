Record BASE_58 = `git log --diff-filter=A --format=%H -- .planning/phases/58-motion-pacing/58-CONTEXT.md | tail -1`.

**Why re-renders matter.** `paint()` ends by calling `renderEncounter()` and `renderRail()`, and a step's render tail usually runs both more than once in one tick. Both functions rebuild their text elements on every call. A typing block started on the first render would therefore be abandoned on a detached node, and the player would see the full text from the second render at once. For a same-content re-render (same rail key, same overlay content), call the typewriter's `adopt` so the block continues on the new elements from its current progress. For new content, call `type`, which cancels the previous block.

**The shell sandbox stubs renderRail.** `loadShellSandbox` replaces `renderRail` with a no-op after running the classic script, and a stubbed function cannot be restored in the same vm context (57-03-SUMMARY records why it wrote the sibling `loadRailDismissSandbox`). Add a `stubRail` option (default true) that skips that stub and wires the real `__mzRailVM` and `__mzRail` from `src/browser/rail.js`, mirroring `loadRailDismissSandbox`'s wiring, so rail typing can be tested through the one shared harness.
