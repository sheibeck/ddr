**The derived stream is shell-reachable.** `engine/rng.js` exports three pure functions: `makeRng(seedOrState)`, `hashString(str)` (FNV-1a) and `derivedRng(...parts)`, which is `makeRng(hashString(parts.join(":")))`. Each call builds a fresh generator and never advances any other instance, least of all the run's `state.rngState` (its own doc comment says so). `src/browser/` modules already import pure engine functions directly (e.g. `combatMenu.js` imports from `../../engine/derived.js`). So `derivedRng(seed, "dressing", depth)` is literally the milestone's `makeRng(hash(seed, "dressing", depth))`, with no engine byte changed and no second hash implementation.

**Why placement ignores features.** `engine/movement.js` clears a feature's `feat` to null when it resolves (dot, trap, chest, tele, climb, gorge), and a save taken mid-floor stores the cleared grid. A placement that excluded current features would therefore reshuffle after every reload. Walls never change after `genFloor` (no runtime write to `.wall` exists outside engine/maze.js; Task 3 pins that with a source check), water is placed once at generation, and every floor starts the party at (1,1) (`genFloor` returns `px: 1, py: 1`). So placement uses only those, and the feature/stairs/party exclusion (DRESS-03) is applied at draw time by `visibleProps`. The one visible consequence: a floor prop whose square held a feature appears there once that feature has resolved. Record this in the SUMMARY as the deliberate reading of D-10 + DRESS-04 (both literally hold: no prop is ever DRAWN on a feature, stairs or party square, and the same seed and depth always place identically).

**Why the outer ring is excluded for wall props.** `draw()` strokes a 6 px maze border over the outermost cells; a banner on the frame would read as part of the border.

**The category table (transcribe exactly).** Stems are the file names without the `set_dungeon_` prefix and `.png` suffix. Lean S is shallow, D is deep, and a dash is neutral. Weight is 1 unless marked rare (0.25).
