<objective>
Audit the actual R8 release artifact for deprecated window and system-UI API calls and for the merged manifest's large-screen attributes, with a reusable, tested scanner, and document edge-to-edge handling and the audit results.

Purpose: DROID-02 ("uses no deprecated window or status-bar APIs Play flags") and DROID-03 (the game category really ships) can only be proven from the built bytecode and merged manifest, not from source. CONTEXT asked for an audit of Capacitor core, SplashScreen and the Play Games plugin; the research answered it from source and left one open question (the splash-screen plugin's legacy methods under R8). This plan answers it from the build and leaves a scanner every future release can re-run.

Output: tools/android-api-scan.mjs and its unit test, the scan and manifest results, the edge-to-edge and audit sections of docs/ANDROID-DISPLAY.md, the RELEASING.md scan step, and the LISTING.md addendum.
</objective>

## Flagged assumptions (surfaced, not silently decided)

- **DROID-02 and DROID-03, edge probe: unclassified, reviewed manually.** The audit's edges are what R8 keeps: library back-compat paths (androidx.core's system-UI code for API 20-29, the splash-screen plugin's immersive and fullscreen paths that capacitor.config.json leaves switched off) can survive shrinking even when unreachable in this app. The scan lists them; it cannot prove whether Play's pre-launch analysis flags them. That verdict comes from the next Play upload's report (milestone-close item).
- **Research assumption A2** (R8 may keep the splash-screen plugin's legacy methods because their gate reads runtime config): answered empirically in Task 2, not assumed.
- **The scanned API list** is the Android 15 edge-to-edge deprecations Play's warning 2 names (bar colour getters and setters, the divider colour, decor-fits) plus the older system-UI-visibility calls and cutout-mode writes. If Play names an API outside the list, add it to the scanner's list and re-run; never remove one.

<interfaces>
- Tools on this machine: JDK at the path in android/gradle.properties `org.gradle.java.home` (C:/Program Files/Microsoft/jdk-21.0.10.7-hotspot/, so bin/jar.exe); SDK at android/local.properties `sdk.dir` (C:/Users/Dell/AppData/Local/Android/Sdk), with build-tools/36.0.0/dexdump.exe and aapt2.exe.
- Archive layouts: an APK has classes.dex, classes2.dex, ... at the root; an AAB has base/dex/classes*.dex.
- `dexdump -d` output: per class a `Class descriptor  : 'La/b/c;'` line; per method a `#N : (in La/b/c;)` line followed by `name : 'm'`; invoke lines contain the target as `Landroid/view/Window;.setStatusBarColor:(I)V`; field writes as `iput ... Landroid/view/WindowManager$LayoutParams;.layoutInDisplayCutoutMode:I`. Output is large: stream it (spawn + node:readline), never buffer the whole thing.
- mapping.txt: class lines `original.Name -> obf.Name:`; member lines under a class, indented, `type name(args) -> obf` (method names can be overloaded).
- Research facts to confirm, not assume: SystemBars uses only WindowInsetsControllerCompat; the splash-screen plugin's SplashScreen class has legacyImmersive / legacyFullscreen (View system-UI visibility) and WindowCompat decor-fits calls, all behind config.isImmersive() / isFullScreen(), which capacitor.config.json leaves false; the Play Games plugin source has none of the APIs.
- Existing tool conventions: a tools/*.mjs script with a header comment, node built-ins only, exit codes 0/1/2 (see tools/roller-repro.mjs, tools/shell-boot-check.mjs). To keep the parser importable by node:test, run main() only when the file is the entry script (compare import.meta.url with the file URL of process.argv[1]).
</interfaces>
