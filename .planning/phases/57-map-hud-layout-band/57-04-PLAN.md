## Correction to CONTEXT's LAYOUT-06 premise — READ THIS BEFORE TASK 1

CONTEXT states, as the reason for this work, that *"`draw()` dims only `tile.dark` cells and nothing reads the counter"* and that *"an already-explored corridor looks identical whether you are in a Table-7 darkness or not."*

**That is not true at HEAD, and it was not true in the build the user tested (`dbcdd66`).** Phase 41 (TERR-03) already shipped a render-window filter:

- `engine/derived.js:837-874` — `mapViewRadius(state)` returns `DARK_VIEW_RADIUS` (1) whenever `inDark(state)` is true and the player has none of the three waivers (Night Vision, a live Amulet-of-Light `light` effect, a lit torch); `inViewWindow(state, x, y)` then hides every cell outside the 3x3 window, *including already-`seen` cells*.
- `inDark(state)` is `tile.dark || c.darkFor > 0` — so a running Table-7 counter drives the filter identically to a natural dark tile.
- `mazeworld.html:1954-1955` and `:2007` — `draw()` reads that filter through `window.__mzMapView` and applies it in BOTH its cell loop and its feature-icon loop.

Verified empirically during planning: a synthetic state with `darkFor: 30` on a NON-dark, fully-`seen` tile with no waivers returns `inDark true`, `revealRadius 1`, `mapViewRadius 1`, and `inViewWindow(9,9) false`. The engine and the existing filter are correct and symmetric.

**What this means for the executor:**

1. **Do not "fix" the filter. Do not touch `draw()`.** There is no missing read of the counter. `shell-terrain-41.test.js`'s pin that `if (!visible(x, y)) continue;` appears exactly twice is the guard on that, and Task 1 adds a characterisation test so no future reader repeats this mistake.
2. The residual, real gap is **communication, not vision**: the 3x3 window looks identical whether it comes from a dark corridor or from a rolled condition, nothing on the map says *why* it closed or *how long* it lasts, and the DARK chip's tap card does not explain the rule. The most likely explanation for the user's device report is a waiver the run actually held (a torch lit after the roll opens the window back up to `Infinity` while `darkFor` keeps ticking and the chip keeps counting down) — which is correct behaviour rendered invisibly.
3. The locked decision still stands and is still worth building: a counter-driven vignette, read through the engine's own `inDark`/`revealRadius` via a new bridge, is a distinct visual state that says *this is the rolled condition, at this radius*. It is additive to the window filter, not a replacement for it.

Record this correction in the plan SUMMARY and in the phase VERIFICATION notes.
