## Flagged assumptions (surfaced, not silently decided)

- **Why `autonomous: false`.** The objective is ruled, so nothing pauses before the search. The plan is non-autonomous only because a failure pattern, a failed confirmation or a tail miss must be handed back mid-plan. The orchestrator answers search-parameter hand-backs itself and relays anything else to the user.
- **200 seeds in the walk, 1,000 to confirm.** Phase 54's fit ran at 200 seeds (USER RULING E), and one 1,000-seed evaluation costs about five 200-seed ones. The ruled yardstick is "at 1,000 seeds", so a 200-seed PASS only nominates a candidate. The confirmation decides.
- **The lock file is not `--out`.** `runSearch` records the lowest-score row as `best`, and that row can be a MISS on the p50 or shape gate while a slightly higher-score row PASSes. The candidate is therefore picked from the log by rule (the lowest-score row with verdict PASS and constraints.ok), and early-lock.json is written explicitly.
- **The tail may move.** The 9 coordinates are global, so a harder base value also acts past floor 12. Every ruled tail target is an upper bound, and a harder tail stays inside it. The risk is the rotation pairs: 79.1-02 had rot30 p90 at exactly deep30's p90. A pair can flip when the fair bot's deep numbers fall faster than the rotation Sorcerer's. That is a tail MISS for the user.
- **Seeds cannot mix in one log.** fit-resume replays by `n` and `dials` and doesn't check seeds. An orchestrator decision to change seeds per evaluation starts a new cycle log.
- **Evaluation cost (estimate).** A 200-seed band evaluation takes 3-8 min with 4 workers, so a block of 10 takes 30-80 min. The 1,000-seed confirmation takes about 15-25 min, and the tail confirmation about 20 min.

<interfaces>
**The block command.** Run it with run_in_background:

`node tools/fit-difficulty.mjs --search --start=<P>/fit/start.json --budget=<N+10> --seeds=200 --workers=4 --log=<P>/fit/early-log.jsonl --out=<P>/fit/early-best.json --transcript=<P>/fit/early-stdout.txt`

- N is the number of numeric-`n` rows in the cycle's log.
- A resumed search replays every logged row whose `n` and `dials` match the walk, at no cost.
- The `elapsed: ... evaluations=K stopped=<pass|budget|plan-exhausted>` line goes to stderr, so read it from the background task's output.

**tools/lib/fit-resume.mjs#runSearch**
- It evaluates the start, then walks each SEARCH_PLAN coordinate in order: +1 step (up to 3 while each improves), otherwise -1 the same way.
- Pass 1 uses full steps and pass 2 half steps.
- It stops at the first row with `verdict === "PASS"` and `constraints.ok`.
- `best` is the lowest `score` seen.

**A band row** (fit-score.mjs#evalRow after 79.2-01):
- `n`, `pass`, `dials`, `score` (`null` in JSON = Infinity, rejected), `verdict`, `misses` (floors 1-12);
- `p50Death`, `p50InBand`, `shape { ok, maxDrop, maxDropFloor, rise, reasons }`;
- `reach20`, `floors[{ L, pL, SL, dS, tail }]`, `classes[3]`, `constraints { ok, reasons, pooledP50, pooledReach5 }`;
- `pace`, `elapsedMs`, and `reason` when rejected.

**A tail row** (tail-score.mjs#tailEvalRow):
- `score`, `verdict`, `misses`, `summaries.{fresh, deep12, deep20, deep30, deep40, rot20, rot30, rot40, troll20}`, `freshMeasured`, `guard`, `constraints` (the rotation pairs).

**The confirmation commands** (single evaluations; each logs row `n: 1`, so every candidate gets its own log files):
- `node tools/fit-difficulty.mjs --dials=<P>/fit/early-candidate.json --seeds=1000 --workers=4 --log=<P>/fit/confirm-1000-c<cycle>n<n>.jsonl --transcript=<P>/fit/confirm-stdout.txt`
- `node tools/fit-difficulty.mjs --objective=tail --fresh=always --dials=<P>/fit/early-candidate.json --workers=4 --log=<P>/fit/tail-confirm-c<cycle>n<n>.jsonl --transcript=<P>/fit/tail-stdout.txt`

**USER RULING F** (54-CONTEXT; the checkpointed-fit memory)
- A failure pattern is any of:
  - a feasible rate under 40% (feasible means `constraints.ok`);
  - a best-score improvement under 10% across the block;
  - one constraint reason rejecting at least 6 of 10;
  - `stopped=plan-exhausted` with no PASS.
- Converging means the best score improved by 10% or more with no failure signal.
- The user wants an honest ETA and a curve table (target / best / gap) at every hand-back.

**Waiting.** Executors have no Monitor tool.
- Use run_in_background and the completion notification.
- In between, use bounded foreground polls: a Bash until-loop capped at 9 minutes per call that prints the transcript's `#n` line count and whether a node process is alive (`tasklist //FI "IMAGENAME eq node.exe"`).
- STALL rule: if no new `#n` line appears for more than twice the slowest evaluation so far (30 min before a block's first new row), check the process. If it has died without its `elapsed:` line, re-run the same block command; resume is free.
- Never leave a process running.

**Values that are never searched here**
- User-ruled: FOE_COUNT_DEPTH, the kneeDepths (12), CONTROL_AT_DEPTH.holdRounds.
- Tail-fitted by 75.3/79.1: FOE_HP_SCALE.perDepthAfter, FOE_HIT_SCALE.perDepthAfter, FOE_ELITE.hpPerRank, CONTROL_AT_DEPTH.resistPerDepth.
- Held and non-ruled, so the orchestrator may promote them: FOE_HP_SCALE.perDepth, ENCOUNTER_DOTS.perDepth, HAZARD_SCALE.perDepth, FOE_COUNT_SKEW, ABILITY_THREAT.base, CAMP_HEAL_FRACTION, FOOD_CLOCK, LOOT_SCALE, FOE_ACCURACY, WANDER_RATE, DOT_MIX.fight, ROUND_DAMAGE_CEILING, STORE_TIER.perDepth.
