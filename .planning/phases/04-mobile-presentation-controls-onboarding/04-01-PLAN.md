<objective>
Deliver the DOM-free touch-control and canvas-sizing math that the Wave-3 maze
viewport (04-06) wires into the live page — the highest-value, fully-testable
core of UX-01 (tap-to-move) and UX-03 (DPR-crisp rendering). These are pure
functions: they take synthetic geometry in and return a cell/direction/size out,
with zero DOM or canvas reads, so `node:test` verifies them headlessly now (per
04-VALIDATION.md Wave 0).

Purpose: Establish the ONE shared transform both the renderer and the tap
hit-tester will read from, eliminating the "compute DPR/cell math twice → drift"
anti-pattern flagged in 04-RESEARCH.md Pattern 1 / Anti-Patterns.

</objective>

| Boundary | Description |
|----------|-------------|
| touch input → engine action | A tap/drag on the WebView viewport is untrusted screen geometry that must resolve to a validated engine action, never a raw state mutation |

## STRIDE Threat Register
| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | resolveTapDirection (out-of-bounds / non-adjacent / unseen tap) | medium | mitigate | resolveTapDirection returns null unless the cell is orthogonally-adjacent AND seen; the direction still flows through dispatch()→applyAction()→engine/movement.js which re-validates walls/bounds server-side-equivalent (04-RESEARCH.md Security Domain V5). No client-computed "reachable" shortcut bypasses applyAction. |
| T-04-02 | Tampering | canvasSizing math (adversarial dpr/cssPx) | low | accept | Pure arithmetic with no security impact; a bad DPR only mis-sizes the canvas visually, never corrupts game state. |
