# Phase 75.1 Plan 09: The hero-cannot-act combat menu shell (RULES-10) Summary

**The combat screen offers exactly one action while the hero cannot act — LET THE ROUND PLAY, wired to the real loseTurn engine action through the same COMBAT_DISPATCH every other row uses — plus real "Can't act" / "Blinded" / "Shrunk" chips, the last two now reporting a measured to-hit/damage effect instead of a placeholder sentence**

## Accomplishments

- **Task 1 — the combat menu while the hero cannot act, and the menu-driven no-soft-lock drivers:** `src/browser/combatMenu.js` gains `heroOutViewModel(vm, heroOut)`, a post-processing transform applied to the otherwise-normal view model whenever `state.combat.heroOut` is set: the prompt names the kind (asleep/stupefied/maddened, via a new frozen `COMBAT_MENU_COPY.heroOutKind` map) and the turns left (singular/plural, mirroring the existing ability-cost pattern); slot 1 becomes LET THE ROUND PLAY (accented, enabled, `dispatch: { type: "loseTurn" }`, sub naming the kind); slots 2-4 keep their own key/label but are disabled with the same reason; every submenu row is disabled too (presentation-only — the row's own dispatch is left alone, since `engine/engine.js#applyAction`'s hero-combat-action conversion already makes any of them safe). Because this is a transform over the normal output rather than a second code path, every existing class branch (Fighter/Bard/Magic User/Thief) runs unchanged underneath it, and "without heroOut the view model is unchanged" needs no separate maintenance. `test/unit/combatMenu.test.js` gained the heroOut shape cases (prompt text, slot enablement, submenu-row disablement, the locked-shape interaction, the class-branch override, the heroOut-absent unchanged pin across all four class fixtures, and the hero Blind/Shrink normal-menu pin) plus a fix to its own flat `COMBAT_MENU_COPY` voice scan (see Deviations). `test/unit/hero-out-shell.test.js` (new) proves the three soft-lock drivers ONE LEVEL UP from `test/unit/hero-out.test.js`'s engine-level proof: reading the view model's own single enabled action and dispatching ITS dispatch payload through `applyAction`, asserting exactly one enabled action at every step.
- **Task 2 — the shell bridge and the Can't act, Blinded and Shrunk chips:** `mazeworld.html`'s `COMBAT_DISPATCH` gains `loseTurn -> window.mzLoseTurn`, defined beside `window.mzAttack` as `engineCombatAction("loseTurn")` — the round's beats, fight log, rail, sounds and paint all run through the identical choke point every other combat action uses. `cb-strike`'s tap handler was rewritten from a hardcoded `window.mzAttack?.()` call to `pickCombatRow(vm.actions[0])` — the SAME row-tap function every submenu row already used — so slot 1 honors its own view-model dispatch (attack normally, loseTurn while the hero cannot act) directly, rather than depending solely on the engine's own conversion as an unstated safety net. `CONDITION_COPY`/`CONDITION_TONE` gain `heroOut` ("Can't act", unit "rds", bad), `heroBlind` ("Blinded", bad) and `heroShrunk` ("Shrunk", bad); `CONDITION_EXPLAIN.heroOut` was rewritten to state the three things the user's ruling requires (the round goes on without you, nothing wakes you early, foes hit you as usual), and `heroShrunk`'s tail sentence now states the halving plainly. `src/browser/conditionEffects.js` gained `WHAT_IF.heroBlind` (a shallow what-if combat with `heroBlind` dropped, mirroring the existing `afraid` builder exactly), so the Blinded chip's tap card automatically leads with the measured one-face range through `paintConditions`'s existing `window.__mzConditionEffect` call — no mazeworld.html change was needed for that wiring since it already calls the bridge for every chip unconditionally.

## Decisions Made

- `heroOutViewModel` is a post-processing transform over the otherwise-normal `vm`, never a parallel branch inside `combatMenuViewModelUnlocked`'s per-class logic — this is what lets the unchanged-menu pin hold for free rather than needing independent upkeep as new classes/branches are added later.
- `cb-strike`'s onclick now reads `vm.actions[0].dispatch` through the same `pickCombatRow` every submenu row uses, instead of a hardcoded bridge call — making the plan's own key-link ("slot 1 while out" dispatches `loseTurn` through `COMBAT_DISPATCH`) literally true, rather than correct only by accident through the engine's own action-conversion safety net.
- `WHAT_IF.heroBlind` mirrors the existing `afraid` builder's shape exactly (a shallow what-if combat with the one field dropped) rather than inventing a new pattern, per 74-07's established convention.
- No `NARRATIVE_ACTIONS`/beat-plan special-casing was needed for `loseTurn`: `dispatchWithNarration` and `planBeat` both already treat every combat action type generically — `narrationLines.js#linesForAction`'s own `type` parameter is unused inside its fold logic — so `loseTurn`'s narration/beat rendering falls out of the existing generic path with zero code keyed on the literal string `"loseTurn"`.
