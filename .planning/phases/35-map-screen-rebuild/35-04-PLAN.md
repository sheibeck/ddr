<objective>
Replace the D-pad with the mock's pointer model on the viewport — tap-to-step (dominant axis, fallback axis), hold-to-inspect, drag-to-pan, pinch-to-zoom — and add the descent gate as a shell pre-dispatch interception on `window.move` that renders `renderMajorOverlay` with THE STAIR DOWN / GO DOWN / NOT YET (MAP-02, MAP-05, rulings 2 and 3, orchestrator decision 5).

**Decisions recorded here:**
- **Decision 5 (descent gate = SHELL pre-dispatch interception):** `engine/movement.js#move` descends unconditionally and synchronously the instant the party steps onto an `exit`/`gate` tile (RESEARCH Pitfall 4), so — unlike the Fight! gate, which reads the engine's own `combat.pending` mid-flight — the stair overlay must show BEFORE any dispatch. `window.move(dir)` checks `stepTargetsExit(dir)` (`S.floor.g[ny][nx].feat === "exit" || === "gate"`, read-only) after the encounter / settle / rail-lock guards; if true it sets `window.__mzStair = { dir }` and renders the overlay instead of stepping. GO DOWN → `window.__mzDescend()` → clears the flag and calls the SAME `stepNow(dir)` every step uses (identical engine call, identical rng); NOT YET → clears the flag and re-renders (the dismissal transition stamps `lastDismissAt`, so `DISMISS_SETTLE_MS` gates the next step). `renderMajorOverlay` is reused unmodified; out-of-combat death is already `renderCombatOver(body, "dead", …)` (Plan 02) — nothing to rebuild.
- **Ruling 2 (tap to move replaces the arrows):** the D-pad, `.mazefoot`, their CSS and the click listener go; keyboard arrows / WASD stay for desktop and funnel through the same `window.move`.
- **Ruling 3 / decision 2 (global lock):** a tap while a rail decision or a failed climb is pending only pulses the card (checked in `tapStep` before any rail line, and again inside `window.move`).
- **Claude's discretion:** the hold detector is a timer armed at pointerdown (450 ms, `tapStep.js`'s `HOLD_MS`) — a pointer still down at 450 ms with ≤ 10 px travel and one finger is a HOLD (the release is then a no-op); a release before that with ≤ 10 px travel and never a second finger is a TAP; `controls.js`'s `classifyPointerGesture` / `TAP_MAX_DURATION_MS` stay untouched (the D-pad-era 350 ms tap/drag split is not the new tap/hold boundary — RESEARCH A5). `ZOOM_MAX` is re-ranged to 2.0 per the spec (0.6–2.0); the default 0.8 stays (RESEARCH Pitfall 8 — the 33-03 SUMMARY's 1.5 is stale). The pinch origin is the party because positionCanvas already centres the party at viewport-centre + pan and the Phase 33 pinch-release recenter zeroes the pan.
