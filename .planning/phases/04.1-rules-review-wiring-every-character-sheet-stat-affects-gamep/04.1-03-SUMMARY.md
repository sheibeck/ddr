# Phase 04.1 Plan 03: Decouple Ration Acquisition from HP-Restoring Food (RATION-01) Summary

**Food purchases and dungeon-tile food finds now heal HP only; Rations became their own dedicated, race-priced, narrated store line item, closing the "silent +1 ration on every food buy" confusion in both acquisition paths at once.**

## Performance

- **Duration:** ~35 min
- **Started:** 2026-09-09
- **Completed:** 2026-09-09
- **Tasks:** 2 (both from 04.1-03-PLAN.md)
- **Files modified:** 6

## Accomplishments

- `STORE_EFFECTS.eatRation` (engine/economy.js) no longer touches `c.rations` — buying food is pure HP healing now.
- A new `STORE_EFFECTS.buyRations` effect and matching "Rations (+1 ration)" stock line, priced at `priceFor(30, race)`, increments `c.rations` by the purchased amount and pushes a `{ type: "rationsBought", amount }` event.
- `engine/encounters.js`'s `findFood` had its `c.rations++` removed too, so the "any food = +1 ration" rule is gone from BOTH acquisition paths together, per the CONTEXT's explicit requirement.
- `src/browser/eventNarration.js` gained a deadpan `rationsBought` narration line ("Stocked up: +N ration(s). At least someone is planning ahead."), satisfying `formatEventsCoverage.test.js`'s narration-coverage guard.
- The Cooking beast-carcass ration path in `engine/combat.js` (the `cooked` event) was left completely untouched, as the plan required.
- `test/unit/economy.test.js` and `test/unit/encounters.test.js` were updated: the old assertion that buying food set `c.rations === 1` was inverted (now asserts UNCHANGED), and three new tests cover the Rations line's existence, price, and purchase behavior.
- `test/parity/harness/comparables.js` gained two new, explicitly documented carve-outs (`stripStoreClosures` filtering the engine-only `buyRations` stock entry by `effectId`, and a new `stripRationsField` helper excluding `c.rations` from the diff) so the economy/encounters prototype-parity suite keeps proving everything it still can (item identity, cost, gold, structure, ordering) without failing forever on RATION-01's intentional behavior divergence from the frozen prototype.

## Files Created/Modified

- `engine/economy.js` — `eatRation` drops `c.rations++`; new `buyRations` STORE_EFFECTS entry; new `RATIONS_BASE_PRICE` constant; new Rations `add(...)` call appended at the end of `openStore`'s stock array (after the premium item, before haggle scaling).
- `engine/encounters.js` — `findFood` drops `c.rations++`, keeps the HP heal and `foodFound` event.
- `src/browser/eventNarration.js` — new `rationsBought` EVENT_NARRATION entry.
- `test/unit/economy.test.js` — inverted the old eatRation/rations assertion; added 3 new tests (Rations line existence + price, eatRation leaves rations unchanged, buying Rations increments rations + emits the event).
- `test/unit/encounters.test.js` — inverted the findFood/rations assertion to assert `c.rations` stays unchanged.
- `test/parity/harness/comparables.js` — `stripStoreClosures` now filters out the engine-only `buyRations` stock entry; new `stripRationsField` helper excludes `c.rations` from `economyComparable`'s diff, both fully documented as deliberate, permanent divergence carve-outs.

## Decisions Made

- **Ration price:** fixed at 30 gold base (race-adjusted via `priceFor`), 1 ration per purchase — a deliberate design value chosen per the plan's own suggested example, documented in a code comment at the constant's definition site.
- **Stock-array insertion point:** the plan's read_first suggested inserting the Rations line "among the existing food adds, before the premium-item rng draws." Doing so shifts the index of every stock entry added after it (potions, lockpicks, armor repair, weapons, armor upgrade, scroll, premium) by +1 on the engine side only — `add()` never consumes rng, so RNG *order* is unaffected either way, but `test/parity/fixtures/action-script.economy.json`'s `buyItem` actions reference hand-verified array indices against the frozen prototype's (unchanged) stock layout, and the SAME `idx` is dispatched to both sides by the parity harness. Inserting mid-array would make identical indices resolve to different items on each side. **Deviation (Rule 1 — bug avoidance):** appended the Rations line as the LAST `add()` call instead, which preserves every pre-existing index untouched and still satisfies the "RNG order unchanged" acceptance criterion.
- **Parity carve-out over fixture rewrite:** rather than editing the frozen golden master or hand-rewriting the parity fixture's indices, added two small, explicitly-commented carve-outs to `comparables.js` (stock-entry filter + `c.rations` field exclusion) — the same established pattern this codebase already uses for the wp/hp label rename and the foe-damage/affliction-loss closures. This was flagged as the expected approach by 04.1-CONTEXT.md/RESEARCH.md itself.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Repositioned the Rations stock-line insertion point to avoid breaking parity-fixture index alignment**
- **Found during:** Task 1, running the full test suite after implementing the plan's literal "insert among the food adds" instruction
- **Issue:** Inserting the new Rations `add()` call among the food adds (as the plan's read_first suggested) shifted every later stock entry's array index by +1 on the engine side, while the frozen prototype (unchanged) kept its original indices. `test/parity/fixtures/action-script.economy.json`'s `buyItem` actions use hand-verified indices dispatched identically to both sides — the shift caused `store.stock.length (12 vs 13)` and (once corrected) would have caused later purchase actions to resolve to the wrong items on the engine side entirely.
- **Fix:** Moved the Rations `add(...)` call to the very end of `openStore`'s stock-building sequence (after the premium item, before haggle scaling) instead. `add()` never consumes rng, so this has zero effect on RNG consumption order — it only changes the stock array's final position, which now only adds a new trailing index rather than shifting existing ones.
- **Files modified:** engine/economy.js
- **Verification:** `npm test` full suite green (510/510), including `test/parity/economy-parity.test.js` and `test/parity/full-suite.test.js`.

**2. [Rule 1 - Bug] Added parity-harness carve-outs for the Rations line and c.rations field**
- **Found during:** Task 1/2, running `npm test` after the economy.js/encounters.js decoupling
- **Issue:** Even after the reposition fix above, `test/parity/economy-parity.test.js` failed with `c.rations (6 vs 5)` right after the first food purchase — an expected, permanent consequence of RATION-01 itself (the engine no longer bumps rations on a food buy; the frozen prototype, being frozen, still does). The `store.stock.length (12 vs 13)` divergence (from the new engine-only Rations stock entry) also needed a carve-out.
- **Fix:** Added `stripRationsField(c)` (excludes `c.rations` from the diff) and extended `stripStoreClosures` to filter out stock entries with `effectId === "buyRations"` before comparing — both new carve-outs are fully documented inline as deliberate, permanent RATION-01 divergences, mirroring the existing `normalizeHpUnit`/`stripAfflictionLoss`/`stripFoeDamageClosures` carve-outs already in that file for analogous reasons.
- **Files modified:** test/parity/harness/comparables.js
- **Verification:** `npm test` full suite green (510/510).
