# Quick 260924-51h: Loop theme.mp3 on the title screen (v2.0) Summary

**What this adds:** `sfx/theme.mp3` now loops across the whole title area: the title screen, the character roller and the title-mode Leaderboards panel. It streams through one looping media element at half the level of the one-shots, on the same Web Audio device as them. On native it starts at launch with no tap. It fades over 500 ms when the player reaches the map (a cut under reduced motion), and it respects the Sound setting and app backgrounding.

## Rulings and choices, as executed

1. **ORCHESTRATOR OVERRIDE (replaces the plan's Task 2 design): stream, don't decode.** The plan called for an `AudioBufferSourceNode` with `loop = true` on a decoded buffer. Instead:
   - One `new Audio()` is created lazily on the first start, with `loop = true`, `preload = "auto"` set at that point, and `src = "./sfx/theme.mp3"`.
   - It is connected once via `ctx.createMediaElementSource(el)` → a music `GainNode` (MUSIC_GAIN 0.5) → the device's `masterGain`, so it shares the Sound gate, the master level and the teardown.
   - Fade is a gain ramp followed by `el.pause()` after `fadeMs`.
   - Restart from the top cancels any pending fade-pause, restores the gain, sets `el.currentTime = 0` and calls `el.play()`. `play()` rejections are swallowed.
   - Without `createMediaElementSource`, the fallback is the bare element with `el.volume = MUSIC_GAIN` and an immediate pause.
   - The element and source node are kept on the device handle for reuse. After Sound Off/On, a new device gets a fresh element, because a source node is bound to its context.
   - The backend signature is therefore `startLoop(handle, trackId, gain)` with no `load` step, instead of the plan's `startLoop(handle, buffer, gain)`. There is no new `fetch(`.
   - Tests use a fake `Audio` element and a fake `AudioContext` against the real `DEFAULT_BACKEND`, plus a fake backend for the player logic.
2. **User ruling 2026-09-24: start at launch on native, with no tap.** Capacitor's `Bridge.java` sets `setMediaPlaybackRequiresUserGesture(false)`, so the shell calls `unlockAudioAndSync()` on native one presented frame after first paint (R-08, lazy). If the WebView still refuses, nothing throws and the first tap rescues it:
   - `open()`'s bounded resume wait keeps a never-settling `resume()` from wedging `unlockSfx` in flight;
   - a later `unlockSfx()` re-resumes the open device;
   - `syncTitleMusic` calls `startMusic()` while the controller wants music, which nudges a stalled loop (re-plays a refused element) without rewinding it.
   The browser dev loop keeps the gesture requirement. A side effect is that on native the 30 one-shot clips also decode just after launch, not on the first tap.
3. **User ruling 2026-09-24: keep playing on the roller.** The controller's `titleVisible` input means the whole title area: the title, `#mw-roller-screen`, or the title-mode panel marker. The roller's `hidden` attribute is observed directly, and no roller or title function body was edited.
   - `roller.start()` un-hides its screen synchronously inside the ENTER tap, so the observer sees title → roller as one state: no restart, no stutter.
   - The roller's commit hides it on the way to the map, which fades the theme.
   - A later roll, such as the dead Hero tab's New Character, restarts it from the top.
4. **Plan discretion kept:** resume after background restarts the loop from the top. No decoded audio is ever held, so the ~50 MB PCM concern no longer applies at all.

## Deviations from Plan

- **Override, not a Rule deviation:** Task 2's player design, described in item 1 above.
- **Rulings applied mid-execution:** the two user rulings in items 2 and 3. Beyond the plan, they added the roller to `titleMusicShowing` and the observer, the native launch-time unlock, the `open()` resume bound, the `unlockSfx` re-resume and the `startMusic` nudge.
- **[Rule 3 - Blocking] CRLF-safe source scans.** `title-music-shell.test.js` matches the pointerdown listener with whitespace-tolerant regexes, because the worktree checkout is CRLF.
- **Fallback scope:** the "AudioContext unavailable" fallback in the override cannot be reached. With no AudioContext, `open()` returns no device, and the Sound gate is the device, so there is no sfx and no music. The bare-element fallback covers a context without `createMediaElementSource`, or one where it throws. Every Android System WebView has both APIs.
