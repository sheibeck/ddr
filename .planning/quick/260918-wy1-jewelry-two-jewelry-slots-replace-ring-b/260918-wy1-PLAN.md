> "We should not have ring/bracelet/amulet as separate equipment slots. We should have jewelry as a slot. Let's allow us to slot up to 2 pieces of jewelry: any combination of rings, bracelets, amulets, and helms."

Replace the four jewelry worn slots (ring, bracelet, amulet, helm — the ones w4n leaves in `WORN_SLOTS`) with ONE slot family, `jewelry`, holding up to TWO pieces: any combination of the 8 JEWELRY rows (content/treasure-tables.js), including two of the same former sub-kind. ## Design decisions (settled here, used everywhere)

**Worn shape — two flat keys `jewelry1` / `jewelry2`, not a two-element array.** `c.worn = { jewelry1?, jewelry2?, cloak? }`; `WORN_SLOTS = ["jewelry1", "jewelry2", "cloak"]` stays the ordered list of concrete KEYS (the address space for actions, the worn map, display and report order). The "jewelry" FAMILY exists only in `slotFor` (which now returns a family), a frozen key table `WORN_KEYS_OF = { jewelry: ["jewelry1", "jewelry2"], cloak: ["cloak"] }`, its inverse `WORN_FAMILY_OF = { jewelry1: "jewelry", jewelry2: "jewelry", cloak: "cloak" }`, `SLOT_FAMILIES = ["jewelry", "cloak"]`, and one helper `freeWornKey(c, family)` (first key of the family with no `c.worn[key]`, else null). Why: (1) every reader that w4n leaves behind (`c.worn[slot]` in useItem/unequipSlot/wearItem/autoWearSlot/sanitizeWorn/emptySlotRows/wornSlotRow/combatMenu/readyWorn/carriedItems via `Object.values`) keeps working with zero shape branching; (2) the action address stays the flat `{ slot }` string the validators, the shell bridges, the combat submenu dispatch and the bot already emit — no new `idx` field, no `{ slot, idx }` arity through actions.js; (3) serialization stays "key -> item object": `sanitizeWorn`'s invariant that every worn value is a non-null non-array object survives, `delete c.worn[slot]` stays the one empty-slot convention (an array would need a null-write second convention), and the parity harness's `stripWornField` is unaffected; (4) the legacy migration is a key rename into the first free jewelry key. The array form would have forced a second addressing scheme through every layer for no behavioural gain.

**A third piece.** Untargeted `equipItem(state, i)` with both jewelry keys occupied -> `equipRejected { item, reason: "jewelryFull" }` (the EXISTING event type with a new reason — no new event type, so the narration/toast coverage guards need no vocabulary change; copy added to `EQUIP_REJECT_TEXT` and the Oracle clause). Targeted `equipItem(state, i, events, target)` — the action gains an OPTIONAL `slot` field (`{ type: "equipItem", i, slot }`, validated against `WORN_SLOTS`) — swaps with exactly that key: the displaced piece drops into bag index i, the same mechanics as the existing cloak swap (no bag-cap check, net zero slots). A target that is not one of the item's family keys -> `equipRejected { reason: "wrongSlot" }`. The rule inside equipItem for a slot item: explicit target wins; else `freeWornKey`; else a single-key family (cloak) swaps with its one key (today's behaviour, byte-identical); else refuse jewelryFull. Shell UX (consistent with the existing Equip / two-tap swap confirm): a BAG jewelry row shows Equip while a jewelry key is free; when both are occupied it shows the swap confirm extended to TWO choices — one button per worn piece ("Swap for {name}") plus No — each dispatching the targeted `mzEquipItem(i, key)`. The cloak keeps its single-choice confirm.

**Old saves (v1.5, the w4n interim, and pre-worn-model).** Tolerant-load only, no gating: `sanitizeWorn` gains a `LEGACY_JEWELRY_KEYS` fold (order: ring, bracelet, amulet, helm) — each legacy key holding an object moves to `freeWornKey(c, "jewelry")`, or, when both are taken, is APPENDED to `c.items` (like w4n's staff fold, so the existing `clampCarry` overflow drop is the only thing that can discard it); the legacy key is deleted. ORDER IS LOAD-BEARING: the fold must run before w4n's generic "delete any key not in WORN_SLOTS" strip, or the legacy pieces vanish. A save with no `c.worn` at all still goes through `reconcileWorn`, which now wears by `freeWornKey` and reports per FAMILY: `{ slot: "jewelry", worn: [names], bagged: [names] }` (`worn` becomes an array — the rail card's count is `worn.length + bagged.length`, so "You were wearing four pieces of jewelry" is right when two are worn and two bagged).

**Content.** All 8 JEWELRY_ROWS get `slot: "jewelry"`; `SLOT_OF` has 15 entries whose values are only jewelry/cloak; the four sub-slot names leave `SLOT_OF`, `WORN_SLOTS`, the validators, `GEAR_COPY.empty`, `RAIL_COPY.wornReconciled.what`, the bot and the docs. Nothing (icons, chips, copy) is keyed on the old names except those leaves — the executor confirms with the comment-stripped greps in the verify gates. Exported rows stay byte-identical (`dropAuthored` still strips `slot`/`act`), so no rolled item shape moves and the fixtures cannot drift.

**Bot.** Kind-driven: `readyWornOfKind(state, ctx, kinds)` scans `WORN_SLOTS` and returns `{ slot, it }` for the first ready, unblocked worn item whose activation kind is in `kinds` — so a glow/tongue/fly/knit item is found in jewelry1, jewelry2 or cloak alike, never by a hard-coded slot name. The bot never calls equipItem; it acquires via takeFind/takeLoot/buy, all of which route through `autoWearSlot` -> first free jewelry key, so it wears up to two pieces and stows the third.

Purpose: one slot family, two pieces, one first-free-key rule; nothing hidden behind a run option; old saves come along.
Output: the three-key worn model in engine + content + tolerant load; the Gear/combat/rail/toast surfaces and the bot re-pointed; tests re-pinned plus the new pins (two of a kind, third refused, targeted swap, legacy migration, validator accept/reject); docs; SUMMARY with the deferred browser checklist.
