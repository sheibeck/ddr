## The ruling (user, 2026-09-19 — verbatim)

> "The Cloak of Ether should literally let you traverse through the stone walls. It makes it so you are not limited to the paths and travel on any squares. Limit it to 10 squares of movement. If your movement ends when you are in a wall, you die."

Correction (user, same day): "there is no d-pad, we are fully tap to move now." — tap-to-move MUST route through solid rock while the effect is live; there is no other movement affordance.

## What changes

Today the Cloak of Ether (content/treasure-tables.js, act kind `ether`, effect 20, cd 80 via `every`) only phases through climbable-wall / crevice FEATURE tiles — the `itemEffectActive(state.c, "ether")` branch of engine/movement.js#move's climb/gorge block, mirroring isFlying. A wall CELL (`g[y][x].wall === true`) is still refused by move's first guard. This task makes it true wall-walking:

1. **Engine rule.** While the `ether` effect is live, `move` accepts a step onto any in-bounds cell (wall or not; the 21x21 border ring counts — the user said "any squares" and the 10-square window bounds it). Feature tiles keep phasing exactly as today. The effect window is 10 squares (`act.effect` 20 -> 10). The cooldown stays 80 — the user's instruction ("cooldown stays 80 unless canon text says otherwise"); 10 + 80 = 90 satisfies the once-a-day rule (effect + cd <= 100, pinned by test/unit/item-activation.test.js) and, decisively, leaves the row's exported `every: 80` / `txt` untouched, so test/parity/fixtures/action-script.economy.json's DECLARED `after.items` Cloak of Ether object (seed 3's Thief) is not moved — zero fixture edits. The row's `txt` ("once every 100 squares") is now slightly generous (usable every 90); the chip and toast state the exact numbers, so it stays unedited. `act` is stripped from exported rows by dropAuthored, so no rolled item shape changes.
2. **Death rule.** The ONLY path that ends a squares-cadence item effect is engine/effects.js#tickSquares, called from exactly one site: move's per-step `c.timers` block (verified by grep: no other tickSquares caller; clearRoundTimers only touches rounds-cadence records; descend deletes only `spell:reveal`). Unequipping the cloak mid-effect does NOT stop the effect — post-w4n an effect is a timer record keyed `item:Cloak of Ether`, never an item read (engine/derived.js#liveItemEffects reads c.timers only), so there is no unequip death trigger to add. The rule gets one home anyway: `resolveEtherEnd(state, rng, events, now)` — if the party's current cell is a wall, push `{ type: "entombed" }` and call the existing terminator engine/death.js#die(state, "entombed", null, rng, events, now) (the same path starvation, falls and gorges use: `die(state, "starve"|"fall"|"gorge", ...)`). New content: `CAUSE_TEXT.entombed` + an `EPITAPHS.entombed` bank.
3. **Nothing in the rock.** move's feature dispatch is by `cell.feat`, and genFloor only scatters features on carved cells, so a wall cell has `feat: null` — but the rule is stated explicitly with a `!cell.wall` gate. newDay's wandering-monster roll (the only other encounter source reachable from a step — the 100-square day boundary; the "encounter clock" IS that roll, per the Phase 41 note in move) keeps its eight d20 draws and skips the fight while the party stands in stone. Foes never move the party (combat.js/encounters.js never write floor.px/py — the only floor writes outside movement.js are fallDark's `dark` flags on non-wall cells).
4. **Seen/fog/render.** engine/maze.js#reveal is a square, wall-agnostic sweep (every cell within the radius gets `seen = true`, rock included) — so a wall cell stepped on is revealed like any visited cell and the neighbouring rock is revealed exactly as it already is around every corridor. Simplest faithful behaviour: no fog change at all. draw() paints the party sprite by (px, py) after the cell pass, unconditionally — it draws on a wall block without any cell-type read, so there is nothing to guard. revealRadius/inDark/inViewWindow read `.dark` on the current cell; a wall cell has no `dark`, so the darkness filter simply doesn't apply in rock.
5. **Tap-to-move (decision).** The shell has NO multi-step route builder: every tap is ONE adjacent step toward the tapped cell (src/browser/tapStep.js#resolveStep — dominant axis first, other axis as fallback — fed by the shell's `isOpen` predicate in mazeworld.html#tapStep). So "route through rock" is the predicate: while ethereal, `isOpen` accepts any in-bounds cell. A tap on a wall cell — adjacent or ten squares away — resolves one step toward it; the player taps again for the next square, watching the chip count down. Because there is no route preview and no multi-square walk, there is nothing to cap: a "route that would outlast the remaining squares" cannot exist — each tap is a single square, and the fatal end was announced at activation and is restated by the chip's warn tone the moment the party is inside stone. Hold-inspect (inspectCell) already returns the SOLID ROCK card for a seen wall without throwing (pinned); while ethereal it gets an in-voice variant.
6. **Phobias in rock (accepted, stated).** engine/phobias.js#isDeadEnd counts non-wall orthogonal neighbours (<= 1 is a dead end), so a Being-trapped-phobic hero stepping into solid rock (0 open neighbours) takes the deterministic trappedPanic hit (clamped to leave 1 hp) and arms Afraid via checkTerrainPhobias — no rng, no new field beyond the existing `trapPanicked` tile marker, and thematically exactly right. Heights/water/darkness reads are all safe on a wall cell (no throws; verified by code read).
7. **Camping in rock (accepted, stated).** makeCamp is not refused inside stone: the ether record is squares-cadence so a camp does not advance it, and the in-stone wandering-monster skip applies to the camped newDay too — solid rock is the safest bed in the dungeon for as long as the cloak holds. No refusal reason is added.
8. **Bot.** tools/lib/tuning-bot.mjs#canStep refuses any wall destination and reads nothing from c.timers; no bot policy ever activates an ether-kind item (chooseFieldItem is torch-only; chooseCombatItem's kinds do not include ether). So the bot never enters a wall and can never be entombed — no behaviour change, one pin.
9. **Old saves.** Tolerant load only: engine/saveState.js#foldLegacyCounters already rehydrates a pre-Phase-39 `c.ether` counter into an `item:Cloak of Ether` effect record; that record (any `left`, even > 10) simply obeys the new rule. No gating, no dual path.
